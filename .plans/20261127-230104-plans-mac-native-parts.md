# Plan: Shipyard native parts — notifications with Allow / Deny, Dock badge, keep awake, reload, update bar (phase 2b)

- **Base**: main

## Goal

Shipyard (`~/Applications/Shipyard.app`) gets the native parts that a browser tab cannot give:

1. A chat permission ask rings one macOS notification with **Allow** and **Deny** buttons. A click on a button answers the ask through `POST /api/chat/answer`, also while the window is hidden or the app is not running.
2. The Dock icon shows a badge with the count of sessions that need the owner (the Board column "Needs you").
3. The app keeps the Mac awake while a run or a chat works, and lets it sleep again when nothing works.
4. The app reloads the page by itself after the dashboard server restarts.
5. When the shell source on disk differs from the source the app was built from, a bar "New version ready" with a **Build and install** button shows. The click builds through the server, shows the progress in the bar, then restarts Shipyard into the new build. A failed build shows the error in the bar, and the old app keeps running.

This is phase 2b of the parent plan "Shipyard, the Mac app of the plans dashboard" (`.plans/20261122-151056-plans-mac-app-parent.md` → Phases → 2b). It takes the two phase 2b open decisions there.

## Decisions taken for the owner

- **The server that owns the chat rings its ask, with or without the watcher lock.** Each chat belongs to exactly one server (`chats` map; one relay connection at a time), so only one server can see an ask, and two servers cannot ring the same ask. The watcher events stay behind the lock (`fence()` in `notifyMac()`); the ask uses the same notifier code without the fence (`notifySend()`). `DASH_NO_NOTIFY=1` still turns it off. Reason: a lock check would drop the asks that the relay replays at start (`chatReattach()` runs before the first watcher tick takes the lock, 2 s later in `startWatcher()`), and the asks of a chat on a server without the lock.
- **One ring per ask, also across a restart (at most once).** The relay replays the running turn after a server restart (`apps/dashboard/chat-relay.mjs`, "A new connection gets the lines of the turn running now again"), so the same `control_request` comes back. The server keeps the request ids it rang in the plan's chat file (`chatFile()` → `rung`, the last 20 ids) and rings an id only once. The id is saved before the notifier runs: a notifier that fails (all notifiers and osascript) loses that one ring, and the ask still shows in the page and on the Dock badge. Reason: "nothing may ring twice" wins over a lost ring, and the badge is the second signal.
- **The ask has its own notification group** `plans-ask-<request id>`, not the plan's `plans-?sel=…` group. Reason: a later "your turn" or a second ask of the same plan must not replace the ask and take its buttons away.
- **Buttons only when the notification shows the full target, unchanged.** The target is the Bash `input.command`, the `input.file_path` of `Edit` / `Write` / `MultiEdit`, or the `input.notebook_path` of `NotebookEdit` (the fields `toolSummary()` reads). The ask gets Allow / Deny only when the tool is one of these five, its target is a string of 1 to 120 characters, all printable ASCII (`/^[\x20-\x7e]+$/`: no new line, no tab, no bidi or other control character), with no `http://` or `https://` (which `notifyParts()` removes), and `redact(target) === target` (no secret pattern). Then the text is the tool and the full target. Every other ask (another tool such as `WebFetch`, `Task` or an `mcp__…` tool, a missing target, or a target that fails a check) shows the tool name alone (no part of the target), has no buttons, and a click opens the plan. For `Edit` / `Write` the notification shows the path, not the new content (the docs say so). Reason: Allow must never run a command or a tool input that the owner could not read in full, and a secret that `redact()` finds never shows. A secret that `redact()` does not know can still show in a short command: macOS hides the text on the lock screen with "Show previews: When unlocked" (the docs say so).
- **The server says which events it rings.** The server fills `/*@RINGS*/{}` in `app.js` with `{ asks, runs }`: `asks` = macOS (or a `DASH_NOTIFIER`) and no `DASH_NO_NOTIFY`; `runs` = `asks` and the watcher on (`WATCH_MS > 0`). Reason: the page must keep its own notification when the server cannot ring. Known limit: `runs` says only that this server's watcher is on; the run outcome rings from the server that holds the watcher lock for this HOME (any server's runs are files that it reads), and a watcher event is at most once (the state is saved before the notification). A page of a second server with the watcher off rings run outcomes itself, so the same outcome can ring twice there; the docs say so.
- **An ask of a test dashboard on another port** gets buttons too, but the app answers on `appURL` (the main dashboard), which gives "The agent no longer waits for this answer.", so the fallback opens the plan. Reason: a chat on a test dashboard is rare (the AGENTS.md test command sets no `DASH_NO_NOTIFY`, so it does ring), and the failure is safe: nothing is allowed.
- **No buttons for AskUserQuestion and ExitPlanMode.** These asks need a typed answer or a plan review; their notification has no Allow / Deny and a click opens the plan. Reason: `chatAnswer()` refuses an AskUserQuestion allow without answers ("Pick an answer first."), and approving a plan unseen is not safe.
- **Allow needs an unlocked Mac.** The Allow action has `.authenticationRequired`; Deny has `.destructive`. Reason: an Allow runs a tool; macOS asks to unlock first when the screen is locked.
- **A failed button answer opens the plan.** When `POST /api/chat/answer` gives `ok: false` (for example "The agent no longer waits for this answer.") or the server does not answer, the app opens the notification's plan URL in the window and shows the window. Reason: the owner sees the real state, nothing fails in silence.
- **The page stops its own system notification only where the server rings.** In `alertUser()`, the browser `Notification` is not shown for "The agent asks for permission" when `SERVER_RINGS.asks`, and for "Run failed" and "Run needs you" only when `SERVER_RINGS.runs` and the plan's project has the pipeline (`p.hasPipeline`: the watcher rings run outcomes only for pipeline projects, `if (proj.hasPipeline)` in `watchProject()`). The card and the chime stay. Generic launcher runs keep the page notification. Reason: no event rings twice, and no event loses its only notification.
- **Shipyard-only flags.** The ask flags (`-askProject`, `-askSlug`, `-askId`) go only to Shipyard and to a custom `DASH_NOTIFIER`; `terminal-notifier` gets the 5 flags of today. `notifyFirst()` accepts `args` as a list or as a function of the notifier file. Reason: an unknown flag must not break `terminal-notifier`.
- **The badge, keep-awake and typing state come from a new page hook `appStatus()`.** The app reads it every 5 s with `evaluateJavaScript`, also while the window is hidden (it is read-only and changes nothing). Reason: the page already has the counts (`boardCol()`, `starting()`, `p.chatting`); the AGENTS.md rule "the app calls the page only through the `window.dashboard` hooks" stays true.
- **"Needs you" = the Board column "needs", or a chat that asks** (`boardCol(p) === 'needs' || p.chatWaits > 0`: `boardCol()` puts a running or failed plan in its own column first, and its ask must still count). **"Works" = a live or starting run, or a busy chat** (`p.live || starting(p) || p.chatting`). Off the dashboard origin (the waiting page), the badge is cleared and the Mac may sleep. Reason: one definition, the same as the Board.
- **Keep awake with a power assertion, not a process.** `ProcessInfo.processInfo.beginActivity(options: .idleSystemSleepDisabled, …)` while working > 0; `endActivity` when it is 0 and at quit. The display can still sleep. Reason: no child process to stop; macOS ends the assertion when the app quits.
- **Restart detection by a boot id that the page also carries.** The server makes `BOOT` (its PID and start time) at start. `GET /api/app` gives it, and the server fills it into the page (`const PAGE_BOOT = /*@BOOT*/'';` in `app.js`, filled like `/*@CHAT_MODES*/[]`), so `appStatus().boot` is the boot of the server that served the loaded page. The app reloads when the two differ. Reason: no race and no double reload — a page that the waiting page loaded from the new server already has the new boot.
- **No reload and no relaunch over unsent text.** The app decides inside the callback of one fresh `appStatus()` call: it reloads (or relaunches) only when that same answer has `typing: false`. `typing` is true when any `TEXTAREA` or text `INPUT` of the page that is not read-only and not disabled (focused or not, also when the change is only spaces) has a `value` that differs from its `defaultValue` (the value the page drew it with), except the sidebar search box `#q`, the palette search `#palq` and the sticky note `#notetext` (the page keeps the note in `localStorage`, `dash-note`); or when the memory of the chat panel holds unsent work of any plan (a non-blank `chatDraft[key]` or a non-empty `chatImgs[key]`: they keep the draft and the images of a chat that is not on screen); or when the Settings form is open with unsaved rows (`settingsDirty()`, the same check `openSettings()` uses). A drawn field with a saved value (a Settings row, `#scandir`, `#bq`) does not count until the owner changes it. Else the reload or relaunch stays pending and the next status call (5 s) checks again. Before a reload the app does one fresh `GET /api/app`, then one more `appStatus()` call, and reloads in that last callback only when the page boot still differs from the fresh server boot and `typing` is still false (no other code runs on the main queue between the callback and `web.reload()`); a flag `reloading` stops a second reload while one is in flight; a failed GET clears `serverBoot`. The search text in `#q` is not kept: it is a filter, not work. Reason: the page does not keep a chat draft, and a reload or a quit would lose it.
- **The hash covers `apps/plans-mac/src/*.swift` and `apps/plans-mac/build.mjs`.** SHA-256 over each file name and content, in name order. Reason: a change to `build.mjs` (Info.plist keys, flags) also changes the app.
- **The update bar is native**, an AppKit bar at the bottom of the window, not page code. Reason: it works while the page is broken or old, and the header title bar script (`headerScript`) stays as it is.
- **The build runs like a generic launcher run; one lock file owns it.** The server takes `CENTRAL/app-build.lock` with an atomic exclusive create (`openSync(lock, 'wx')`) before anything else; a second POST on any server fails there ("A build is already running."). The build's own shell writes its PID into the lock as its first command, and its `EXIT` trap writes the exit code to `CENTRAL/app-build.exit` and then removes the lock. So the build process, not a server, holds and releases the lock, also across a server restart. The server starts it detached (`bash -lc`, as `launchGeneric()`), output in `CENTRAL/app-build.log`, `{ startedAt, hash }` in `CENTRAL/app-build.json` (written before the spawn). The shell runs with `argv0: 'app-build'`, so `ps` shows `app-build` at the start of its command line. A lock is stale only when its PID is gone (`pidGone(pid)`, as `bootstrapUpgrade()`), or when `psCommand(pid)` answers and does not start with `app-build` (a reused PID); a `ps` that fails (null) says nothing, so the lock stays live, as `lockState()` judges the watcher lock; an empty lock is stale only after 60 s (the shell never started). A stale lock is moved away with the rename of `takeLock()`: rename it to `app-build.lock.stale.<server pid>`, read it again, and put it back (`linkSync`) when its text or mtime is not the one judged stale, so a server never removes the new lock of another server. Then the POST takes the lock with `wx`. State: `running` while a live lock exists; else `done` for exit code 0, `failed` for another code or for a stale lock with no exit file ("The build stopped."); `null` with no JSON and no lock. An unreadable JSON file reads as none. The exit code is the one owner of the end state, the log file is the full output, and there is no timeout and no kill. Reason: two servers or a restart must never run two builds on the same `.new` / `.old` paths of `installApp()`.
- **`build.mjs` refuses to install a build whose source changed while it compiled.** It takes `shellHash(HERE)` before the compile, writes it as `ShellHash`, and takes it again after `codesign`; when the two differ, it exits 1 with "The source changed during the build. Build again." and installs nothing. Reason: the `ShellHash` of an installed app must name the source it was built from.
- **`DASH_BUILD_APP=<file>`** names the program that `POST /api/app/build` runs instead of `node apps/plans-mac/build.mjs`, for the tests. Off macOS, with no `DASH_BUILD_APP`, the endpoint refuses ("Shipyard builds only on macOS."). Reason: mirrors `DASH_NOTIFIER`.
- **Relaunch by PID.** After a `done` build, the app relaunches when the page has no unsent text: an `appStatus()` answer with `typing: false`, or a page that cannot have the hook (off the app's origin, as the waiting page, or a page whose `appStatus()` gives null because it is older than this plan). Only `typing: true` holds it. Then the app starts `/bin/sh -c 'while kill -0 "$1" 2>/dev/null; do sleep 0.2; done; exec /usr/bin/open "$2"' sh <own pid> <~/Applications/Shipyard.app>` and then calls `NSApp.terminate(nil)`. `kill -0` only checks that the PID lives. When the source changed again after that build, the new app shows the bar again (its `ShellHash` differs from the server's). Reason: AGENTS.md "Never stop processes by name"; the app stops only itself.
- **The notification answer keeps the app awake until it ends.** `userNotificationCenter(_:didReceive:withCompletionHandler:)` calls its completion handler only after the `POST /api/chat/answer` answer or the fallback (open the plan) has run, also when the click started the app. Reason: macOS may suspend an app that called the handler before its network call ends.
- **No events.jsonl line for an ask.** The ask is a chat state (`/api/chat` → `waits`), not a watcher event. Reason: `addEvents()` is the watcher's record of its own ticks.

## Hard rules

- **Restart after dashboard changes.** The plan changes `apps/dashboard/server.mjs` and `apps/dashboard/page/app.js`. The run is in a worktree and does not restart. Its report lists under Open items: "after merge and `git pull`: run `pgrep -fl chat-relay.mjs`; only when it shows that the live chats run under the relay, run `npm run restart`; then reload the dashboard. Then run `npm run build-app` once by hand (the 2a app has no update bar), quit Shipyard (⌘Q) and open it again." `server.mjs` imports `shellHash` from `apps/plans-mac/build.mjs`, so a later change to `build.mjs` also needs this restart. The tests start their own servers.
- **No npm dependencies.** The server uses `node:crypto` (already imported, `createHash`) and `node:child_process`. `build.mjs` uses `node:crypto` and `node:fs`. The Swift code uses only `AppKit`, `UserNotifications`, `WebKit` and `Foundation` (`URLSession`, `ProcessInfo`, `Process`). `package.json` does not change.
- **Public repo: no private data.** No domain, path or name goes into the source. The app's URL comes from Info.plist as today. Tests use made-up projects (`acme`, `demo`), `https://shipyard.test`, `https://dash.example.test` and fake request ids (`req-test-1`).
- **Global rules affect every project.** Not touched: no change to the root `CLAUDE.md` or `skills/`.
- **Never stop processes by name.** No `pkill`, `killall` or `NSRunningApplication.terminate` of another app. The app quits only itself (`NSApp.terminate`) after a done build. The helper shell waits with `kill -0 <pid>` (a check, it sends no signal) and runs `open`. The server never stops the build: it ends by itself. A source test checks that `main.swift` has no `pkill`, `killall` or `forceTerminate`. `apps/plans-mac/AGENTS.md` gets the new rule text.
- **Tests for logic changes.** `shellHash()` and the new `infoPlist` key in `apps/plans-mac/test/build.test.mjs`; the Swift source checks and the `appStatus` hook contract in the same file; `GET /api/app`, `POST /api/app/build` and the page parts in `apps/dashboard/test/dashboard.test.mjs`; the ask notification end to end in `apps/dashboard/test/watcher.test.mjs`; `notifyFirst()` with per-file args in `apps/scout/test/scout.test.mjs`. All run with `npm test`.
- **Docs: current state only.** `docs/plans-dashboard.md` → "Mac app" and the environment table describe the new state in the present tense; `apps/plans-mac/AGENTS.md` gets the changed rules; the parent plan marks 2b as planned.

## Endpoint access

| Endpoint | Method | Access |
| --- | --- | --- |
| `/api/app` | GET | The same as every `/api/*` route: loopback only, a local host name, same-origin or no Origin (`crossSiteReason()`). No rate limit: it hashes the Swift sources and `build.mjs`, reads the build files in `CENTRAL`, and runs one `ps` call while a build lock exists. |
| `/api/app/build` | POST | The same as every `/api/*` route. One build at a time, also across a server restart (a second POST while one runs gives `{ ok: false }`). |
| `/api/chat/answer` | POST | Unchanged. Shipyard calls it from native code (`URLSession`, no Origin header, no `Sec-Fetch-Site`), which `crossSiteReason()` lets through as it lets `curl` through today. |

## Contracts

The project has no shared contract source. Interfaces across a boundary:

- **`GET /api/app`** (new) → `{ boot: string, shellHash: string | null, build: null | { state: 'running' | 'done' | 'failed', startedAt: ISO string, endedAt: ISO string | null, hash: string | null, output: string } }`. `shellHash` is null when the source cannot be read. `build` is null when neither `CENTRAL/app-build.json` nor the lock exists. `build.hash` is the source hash at the build start. `endedAt` is the time of the exit file. `output` is `CENTRAL/app-build.log` with `redact()` applied to each line, then its last 4000 characters.
- **`POST /api/app/build`** (new), no body → `{ ok: true }` or `{ ok: false, output }`.
- **Info.plist** (changed): a new key `ShellHash` = `shellHash()` at build time.
- **Shipyard notifier flags** (changed): next to `-title`, `-subtitle`, `-message`, `-open`, `-group`, a permission ask adds `-askProject <name> -askSlug <slug> -askId <request id>`. With them, the notification gets the category `plans-ask` (actions `allow`, `deny`) and `userInfo["ask"] = { project, slug, id }`.
- **`window.dashboard.appStatus()`** (new hook) → `{ needs: number, working: number, typing: boolean, boot: string }`.
- **Page fill marks** (new): `/*@BOOT*/''` and `/*@RINGS*/{}` in `app.js`, filled with `JSON.stringify(BOOT)` and `JSON.stringify({ asks, runs })` in the `PAGE` fill chain of `server.mjs`.
- **`notifyFirst(list, args, opts)`** in `apps/scout/scout.mjs` (changed): `args` is a list (as today) or a function `(file) => list`.

## Breaking changes

- `notifyFirst(list, args, opts)` — consumers: `notify()` in `apps/scout/scout.mjs`, `notifyMac()` in `apps/dashboard/server.mjs`, the test in `apps/scout/test/scout.test.mjs`. A list still works as before; only the new function form is added. None break.
- `infoPlist({ url, version })` — consumers: `build.mjs` and `build.test.mjs`. `hash` is optional (an empty `ShellHash` when not given), so the old test call still works.
- `alertUser()` — the page no longer shows a browser notification for "The agent asks for permission", nor for "Run failed" / "Run needs you" of a pipeline project. The server rings them on the Mac. When the server cannot ring them (`SERVER_RINGS.asks` / `.runs` false: off macOS with no `DASH_NOTIFIER`, `DASH_NO_NOTIFY=1`, or the watcher off), the page keeps its own notification. Written in the docs.
- `notifyMac()` — same signature and behaviour; its notifier part moves into `notifySend()`. Consumers: the `note(…)` calls in `watchProject()`.
- `apps/plans-mac/AGENTS.md` rule "The app and build.mjs never stop processes. A new build is used after the owner quits the app (⌘Q) and opens it again." changes: the app may quit itself after Build and install.
