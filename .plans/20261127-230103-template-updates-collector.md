# Plan: Template updates collector (bootstrap fleet upgrade, phase 2)

- **Base**: main
- **Parent**: .plans/20261124-123512-bootstrap-fleet-upgrade-parent.md
- **Waits for**: claude-config plan 20261127-230102-cross-repo-defect-tickets merged

## Goal

Each unattended upgrade run (`skills/bootstrap-project/scripts/upgrade-run.mjs`) writes the template updates it found to a local wave list, not only to its PR body. A "Collect template updates" chip on the dashboard starts one collector run. The collector run works in a claude-config worktree on `auto/bootstrap-collect-<hash>`, removes duplicates, writes each feature once in generic form into `skills/bootstrap-project/templates/`, and opens one draft PR to claude-config that lists each feature and the projects that found it. This is phase 2 of the parent plan ("Template updates collector"). Phase 3 (waves) later starts the same collector by itself after the last run of a wave.

## Decisions taken for the owner

- **The wave key is a new templates-only hash, `templatesHash()`, not the `--status` hash.** `renderHash(params, repo)` in `render.mjs` hashes the output for one project's answers, so two projects on the same templates have different hashes and one wave file per `renderHash` would never hold two projects. `templatesHash()` hashes the files under `skills/bootstrap-project/templates/` (path and content), 16 hex characters like `renderHash`. Phase 3 needs the same key ("a new template hash starts a wave").
- **Wave lines are append-only, three kinds: `run`, `update` and `collected`.** Several upgrade runs of one wave can write at the same time; `appendFileSync` of one short line per call never mixes two writers' lines, a read-modify-write could lose one. The reader drops a second line with the same `id`, so every append is safe to repeat.
- **An upgrade run saves its wave lines before its commit, and every later run of the same repo appends what is missing.** Right before the commit, every run that reaches the commit writes `<repo>/.plans/auto-runs/bootstrap-upgrade-updates-<hash>.json` (gitignored): `{ runId, runAt, templatesHash, branch, lines }`, where `lines` start with one `run` line (`of` = the number of update lines, also 0) and then the update lines. `flushWave(repo, baseSha)` handles every saved file of the repo (any `<hash>`): it appends only with proof that this run's commit exists: the saved `commit` SHA (written into the saved file right after `git commit`) exists locally (`git cat-file -e <sha>^{commit}`) or is the tip or an ancestor of the remote branch; with no saved `commit` (a crash between the commit and that write), the proof is a branch tip commit with the message `<PR_TITLE> (<hash>)` and a commit time not before `runAt`. Every git call in `flushWave()` goes through `run()`, never `must()`, and a branch that is gone (deleted after a merge) gives "no proof", so `flushWave()` never fails the upgrade run; it then appends each saved line whose `id` the wave file lacks, into the wave of the saved `templatesHash` (never a recomputed one). A saved file with no proof whose branch has no worktree is deleted (a run killed before its commit, or a branch removed after its PR, whose lines were appended before). It runs right after the commit, and in `upgrade()` after the fetch and before every resume branch (open PR, `--no-push`, push retry), so no resume path skips it. The wave file itself is the record of what was written: no `waveWritten` flag. A failed append logs one redacted line and does not fail the run; the next run tries again. The saved file of the hash is also deleted when a fresh worktree is made and when a run fails before its commit, so the lines of thrown-away work never reach the wave. A run that ends in state `same` after the Claude step ("nothing to commit") has nothing to throw away, so it appends its `run` line and its update lines right away; a run that ends in `same` before the Claude step ("nothing to upgrade") appends a `run` line with `of: 0`. The PR number is not stored in the line: the reader takes it from the repo's `.plans/auto-runs/bootstrap-upgrade.json` when its `hash` is the line's `renderHash` and its state is `pr`.
- **Each upgrade run gets a random run id (`randomUUID()`) and a run time `runAt` (the time it saved its lines); a line id is `<runId>#<i>`, and each line has `runAt`; the `run` line has `of` (the number of update lines of its run).** Two repos can start in the same millisecond, so `startedAt` is not unique. Per repo, the reader takes the complete run (its `run` line and all `of` update lines present) with the newest `runAt`; a partial run and an older run that a delayed retry appends late are ignored. A newer complete run with `of: 0` makes the repo's older updates of that wave count no more (the repo no longer has them to give).
- **Each update line carries `names`: the private names of its project (folder name, and `project.name`, `project.title`, `project.client` and the owner and repo of `project.remote` from its `bootstrap.json`).** The collector uses them only for its generic check; they never reach the session, the PR or the changelog. A name shorter than 3 characters, a contract default (`Default`, the `project.client` default in `contracts.md`) and a value that the collector repo's own `.claude/bootstrap.json` has (for example this repo's client `Personal`, already public here) are left out, so a common value does not block every template edit. Each name is escaped before it goes into a pattern. One helper, `privateNames(wave, ownParams)` in `collect-run.mjs`, gives the names after these leave-outs; both the `<project>` replacement in `task.json` and the generic check use it, so a left-out value (for example `Personal` in "a personal access token") is neither replaced nor refused.
- **The unattended upgrade session adds two optional fields to each `templateUpdates` item: `repoPath` (the changed repo path whose file has the feature) and `excerpt` (the lines of that file that make the feature, at most 80 lines).** The collector session cannot open the project repo, so it needs the feature text in the wave line. `checkDecisions()` keeps `repoPath` only when it is a changed path and cuts `excerpt` to 8000 characters. Both are optional, so a session that leaves them out still passes.
- **The free-text fields of a wave line go through `redactText()`, and every field that reaches the collector session is cleaned again.** Before `task.json` is written, the collector replaces each name of `privateNames()` with `<project>`, each home path (`/Users/<x>`, `/home/<x>`) with `<home>`, and runs `redactText()` on `path`, `repoPath`, `feature`, `why` and `excerpt`. Only these free-text fields are redacted (in the upgrade run and again here); the structured fields (`id`, `run`, hashes, `branch`, `repo`, `names`) stay as they are, because `redactText()` would turn a UUID into `<id>`.
- **The collector PR body names the projects by alias (`P1`, `P2`, …), and the local run report maps each alias to the project folder name and its upgrade PR.** claude-config is public (hard rule "Public repo: no private data") and a project folder name can be a client name. The owner still sees which projects found a feature, in the report that the dashboard opens with 📄.
- **A `collected` line lists the exact update ids that one collector round took (features and skipped alike), with its `round` and `branch`.** An update id that no `collected` line lists is pending. Round 1 uses `auto/bootstrap-collect-<hash>`; round `k` ≥ 2 uses `auto/bootstrap-collect-<hash>-<k>`, where `k` = the highest `round` in the wave + 1. `appendCollected()` does nothing when a line for that `branch` already exists, so a repeated append never adds a round. While any collector PR is open (of any wave), a new run is refused: one collector PR at a time in all of claude-config. The ids of a closed PR count as collected: closing is the owner's no. To take them back, the owner sets `ids` of that line to `[]`; the `round` stays, so the next run uses a new branch.
- **A collector run has its own id (`collectId`, `randomUUID()`) and carries `collectId`, `ids`, `round`, `branch` and `hash` over from the previous status (the first status write of a run keeps them, unlike `upgrade()`, which writes `hash: null`), as `upgrade()` carries `session` and `replaces`.** At the start, before it picks a wave, when the previous status names a branch that no `collected` line of the status's own `hash` has, the run resumes that branch in that wave first: an open, merged or closed PR → `appendCollected()` into that wave with the saved `ids`; a committed branch with no PR → publish with the saved body (and the base-aware changelog check); a branch with no commit (a crash before the commit, or before the `collected` line of a `same` run) → drop it, clear `branch` and `ids` in the status, its ids stay pending, and the run goes on as normal. The global open-PR check is one call: `gh api repos/{owner}/{repo}/pulls?state=open` and a filter on head refs that start with `auto/bootstrap-collect-`; an open one stops the run in state `pr` with that PR, its hash and its branch. The dashboard allows a start when a wave is pending, when the status needs such a resume, or when the last run is `failed`, and the chip shows "collect failed" (click to retry) exactly in that last case, so every chip click has a server path; for state `pr` the chip is a link to the PR and starts nothing. This covers a crash before and after `gh pr create`.
- **A collector session that skips every update, or changes no template file, ends in state `same` with no commit and no PR, and appends a `collected` line with `pr: null` and all ids (first drop the worktree and branch, then the line, then the status; a crash between two of these only repeats work).** The skip reasons go into the run report.
- **The collector run mirrors the upgrade run: a headless Claude session works only in a temp run folder, and the script writes the worktree.** The session gets a copy of `templates/`, the de-duplicated updates and its rules (`references/collect.md`), and writes `out/<template path>` files and `collect.json`. The script checks them before it writes anything. It compares each `out/` file with the file in the worktree, never with the run folder copy, and refuses the run when the run folder's `templates/` copy changed during the session (a hash of the copy before and after).
- **The script refuses output that is not generic, in every public channel.** Every added line of an `out/` file (a line that the file it replaces does not have, so a moved line counts as added), every `out/` path, and every text that Claude wrote in `collect.json` (feature `title` and `why`, skipped `reason`, `questions`) is checked for each private name of the wave (`names` of each update line, whole name, case-insensitive, at word bounds), an email, a home path (`/Users/`, `/home/`), a secret, and a redaction marker (`<project>`, `<home>`, `<redacted>`, `<email>`, `<id>`, `<ip>`) that would copy cleaned text into a template. There is no exemption for a name that occurs elsewhere in the templates. A hit fails the run with no commit and names the hit in the report; a project with a very common folder name (for example `api`) can then need a hand fix, which is the safe side. The PR body and the changelog entry are built only from those checked texts.
- **The secret check is its own narrow pattern, not `redactText()`.** `redactText()` matches `token`, `key`, `secret` or `password` followed by a space, so ordinary template prose ("a token that stays valid", "a cache key") would fail. The collector matches only an assignment with a long value (`/\b(token|key|secret|password)\s*[=:]\s*['"]?[A-Za-z0-9_\-]{12,}/i`), known key prefixes (`sk-`, `ghp_`, `gho_`, `xox[bp]-`, `AKIA`) and credentials in a URL.
- **The collector verifies with `node --test test/bootstrap-project.test.mjs` in the worktree.** That test renders the templates with the example answers and runs `verify.mjs`; a failure fails the run before the commit.
- **The collector PR carries a `changelog.d/` entry written by the script**, not the `no-changelog` label: a template update changes every project, and `AGENTS.md` says every PR adds one. `changelog.d/AGENTS.md` says "Use `/changelog-entry`"; that skill needs a session in the repo, and this run is a script with no chat, so the script writes the same format (`changelog.d/README.md`) from the checked feature texts. The file is `changelog.d/<YYYYMMDD>-<slug>.yaml` (the `<date>-<short-slug>.yaml` form of `changelog.d/README.md`; the slug holds the round, so two rounds never share a name); the script refuses to write it when the file exists. The verify step runs `node .claude/scripts/changelog-validate.mjs` (format check) before the commit, and `publish()` runs `node .claude/scripts/changelog-validate.mjs --base origin/<base>` before every push, on the first publish and on every resumed publish, so a retry never skips it (a failure leaves the run `failed` with the commit kept, as an upgrade commit is kept). The entry is `audience: internal`, `scope: bootstrap-project`.
- **The chip sits in the project header of the claude-config card (the project whose root is the collector repo), in the same slot as the "bootstrap update" chip.** That card never shows a bootstrap chip (`bootstrapCheck()` gives `null` for `DASH_REPO`). When claude-config is not a registered project, no chip shows; the POST route still works.
- **The collector repo is `DASH_REPO`, with an env override `DASH_COLLECT_REPO` for tests.** The dashboard tests must not start a run in the real checkout; this mirrors the existing `QA_HOME` and `CLAUDE_TMP` overrides.
- **The collector session merges duplicates by meaning, not by text.** The script only groups exact duplicates; `collect.md` tells the session to merge updates that describe the same feature in one feature entry with all their ids. In real runs `templateUpdates[].path` is often a repo path (`.claude/scripts/auto-pipeline.sh`); `collect.md` says to map it to the template path (`dot-` prefix, `.tmpl` suffix, `core/` or `modules/<m>/`). An update with no `excerpt` whose feature text is not enough to write the template change is skipped with the reason "no excerpt".
- **The chip shows the newest pending wave only.** One collector PR at a time keeps the owner's review to one PR; an older pending wave shows after the newest one is collected. `/api/state` reads the wave files through a cache keyed by the folder's file names, sizes and mtimes, so an unchanged folder is not read again.
- **The shared lock and spawn code of `bootstrapUpgrade()` moves into one helper that both starts use**, so the stale-lock rules stay the same in both places.

## Hard rules

- **Restart after dashboard changes.** The plan changes `apps/dashboard/server.mjs` and `apps/dashboard/page/app.js`. The pipeline run is in a worktree and does not restart; its report lists under Open items: "after merge: run pgrep -fl chat-relay.mjs, then npm run restart, but only when it shows that the live chats run under the relay".
- **No npm dependencies.** The new scripts use only Node built-ins (`node:fs`, `node:path`, `node:os`, `node:crypto`, `node:child_process`). `package.json` does not change.
- **Public repo: no private data.** The wave files live under `~/.claude/` and are never committed. The collector checks every output file for project names, emails, home paths and secrets, and the PR body uses aliases. Tests use made-up names (`acme-api` in the existing upgrade tests, `nimbus-shop`, `nimbus-web`, `Nimbus Example Co`, `Ana Example`, `ana@example.test`).
- **Global rules affect every project.** `skills/bootstrap-project/SKILL.md` gets one routing line for `--collect --unattended`; `references/collect.md` is read only by the collector session. No root `CLAUDE.md` change.
- **Never stop processes by name.** No step stops a process. The tests stop nothing by name; the dashboard test server is stopped by its child handle, as today.
- **Tests for logic changes.** New `test/bootstrap-waves.test.mjs` and `test/bootstrap-collect-run.test.mjs`; new cases in `test/bootstrap-upgrade-run.test.mjs`, `test/bootstrap-project.test.mjs` and `apps/dashboard/test/dashboard.test.mjs`. All run with `npm test`.
- **Docs: current state only.** `references/contracts.md` and `docs/plans-dashboard.md` describe the wave list, the collector run and the chip in the current state, one line per paragraph.

## Contracts

The project has no shared contract source. These shapes are documented in `skills/bootstrap-project/references/contracts.md`:

- New: wave list `~/.claude/pipeline-dashboard/bootstrap-waves/<templatesHash>.jsonl`.
  - `run` line: `{ v: 1, kind: 'run', id: '<run>#0', run, runAt, of, at, templatesHash, repo, project, renderHash, branch }`.
  - `update` line: `{ v: 1, kind: 'update', id, run, runAt, at, templatesHash, repo, project, names, renderHash, branch, path, repoPath, feature, why, excerpt }`. `run` is the upgrade run's `runId` (`randomUUID()`); `id` is `<run>#<i>` (`i` from 1); `project` is `path.basename(repo)`; `names` are the private names for the generic check. The reader skips a line whose fields are missing or of the wrong type, and a second line with the same `id`.
  - `collected` line: `{ v: 1, kind: 'collected', at, templatesHash, round, branch, collectId, pr: { number, url } | null, ids: [id] }`; one line per `branch`.
- New: `<repo>/.plans/auto-runs/bootstrap-upgrade-updates-<hash>.json` (`{ runId, runAt, templatesHash, branch, commit, lines }`, the saved wave lines of an upgrade run, gitignored).
- New: collector run status in `<claude-config>/.plans/auto-runs/`: `bootstrap-collect.lock`, `bootstrap-collect.json` (`{ state, step, hash, templatesHash, base, branch, worktree, runDir, pid, pr, error, startedAt, endedAt, session, collectId, ids, round }`, states `running | pr | committed | same | failed`, steps `prepare | claude | apply | verify | commit | push | pr`), `bootstrap-collect.log`, `<slug>-pr-body.md`, `<slug>.md` (report, read through `GET /api/report?slug=<slug>`), where `<slug>` is `bootstrap-collect-<hash>` or `bootstrap-collect-<hash>-<k>`.
- New: collector task and output in the run folder: `task.json` `{ hash, updates: [{ ids, projects, path, repoPath, feature, why, excerpt }] }` (`projects` are aliases), `templates/` (a copy), `refs/collect.md`, `refs/lessons.md`; Claude writes `out/<template path>` and `collect.json` `{ features: [{ title, why, ids, files }], skipped: [{ ids, reason }], questions: [string] }`.
- Changed: `decisions.json` `templateUpdates` items get the optional `repoPath` and `excerpt`.
- Changed: upgrade run status `bootstrap-upgrade.json` gets `templatesHash` and `runId`.
- Changed: `/api/state` project entry gets `bootstrapCollect` (`{ wave: { hash, updates, projects, at, round } | null, run: <collector status> | null }`, only on the collector repo's card, else `null`).
- New: `POST /api/bootstrap-collect { hash? }` → `{ ok: true }` or `{ ok: false, output }`; 400 for a `hash` that is not 16 hex characters.

Consumers: `apps/dashboard/page/app.js` (the chip), the collector script, the dashboard tests.

## Breaking changes

- `checkDecisions()` (`upgrade-run.mjs`): its `templateUpdates` items now always have `path`, `feature`, `why`, `repoPath`, `excerpt` as strings. Consumers: `prBody()` (reads `path`, `feature`, `why` only) and the tests. No break.
- `runClaude()` in `upgrade-run.mjs` keeps its signature and behaviour; it calls the new `claudeSession()`.
- `bootstrapUpgrade()` keeps its answers (`{ ok }` / `{ ok: false, output }` texts); only its lock and spawn code moves into the helper. The existing dashboard tests cover it.
- `openUpgradeReport(project, hash)` in `app.js` becomes `openUpgradeReport(project, hash, kind = 'bootstrap-upgrade')`; the shared `data-bsreport` handler passes `el.dataset.kind` (the collector button sets `data-kind="bootstrap-collect"`, the upgrade button sets none). The pane title and the `/api/report` slug use `kind`. The only callers are that handler and the two chips.
- `/api/state` gains one field; old pages ignore it. None else.
