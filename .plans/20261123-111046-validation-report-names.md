# Plan: Validation reports name their author

- **Base**: main

## Goal

A validation report's file name says which validator wrote it. Today Claude's `plan-validator` writes `<plan>-validation-<n>.md` and Codex writes `<plan>-codex-raw-<n>.md`, so a reader cannot tell from the name that the first one comes from Claude. After this plan, a new round writes `<plan>-validation-claude-<n>.md`, `<plan>-validation-codex-<n>.md` and the decision log `<plan>-validation-round-<n>.md`. Every file of a round sorts together and has the word "validation", and all three files of one round have the same `<n>`.

The plan also fixes three defects in the writers and readers of these files:

- `plan-lanes.mjs` never counts a Codex round: its pattern `-(validation|codex)-(\d+)` does not match `-codex-raw-<n>`. `node .claude/scripts/plan-lanes.mjs --json` shows `"codex": 0` for every plan that has `-codex-raw-<n>.md` reports.
- The dashboard counts files, not rounds (`validationRounds` in the server). A plan with 4 rounds from both validators shows "validated ×8".
- The round number has two rules. `/skill-auto-validate-plan` starts at round 1 on each run ("Rounds (max 4)": "For round `n` = 1"), and the `plan-validator` agent takes "the next free number". A second run can overwrite the Codex report and the decision log of round 1, and the Claude report can get a number that differs from its decision log. `ls .plans/.validations` shows the event-watcher plan with rounds up to 8 from two runs: the second run went on past 4 only because it chose its numbers by hand.

The change goes into the bootstrap templates. Another project gets it when its owner runs `/bootstrap-project --upgrade` there and says yes to each changed file (the skill shows the diff of each file first). The dashboard is one server for all projects, so its counting fix applies to every project after the restart.

## Contracts

The file names in `.plans/.validations/` are a contract between the writers (the `plan-validator` agent, `/skill-auto-validate-plan`, `/apply-validation`) and the readers (the dashboard's `validationRounds`, `plan-lanes.mjs` → `validationRounds`, which `/plans-parallel` reads in the text digest). `skills/bootstrap-project/references/contracts.md` lists it in the `.plans/` row, and lists the `plan-lanes` JSON shape (`recommendedBatch: [{ slug, file, areas, validation: { claude, codex } }]`). The plan changes both.

- Validator reports, new names: `<plan-base>-validation-claude-<n>.md`, `<plan-base>-validation-codex-<n>.md`.
- Validator reports, old names that the readers still accept: `<plan-base>-validation-<n>.md` (Claude) and `<plan-base>-codex-raw-<n>.md` (Codex). These are the only old names a writer produced: `git log -S "codex-raw" -- skills .claude` shows `-codex-raw-` since the first commit, and `git log -S "-codex-<n>" -- skills .claude` finds no writer of `-codex-<n>` (only the docs demo, step 11).
- Decision log: `<plan-base>-validation-round-<n>.md` (new), `<plan-base>-round-<n>.md` (old). The readers count neither.
- Not changed: the snapshot `<plan-base>-pre-round-<n>.md` (gitignored by `*-pre-round-*.md`) and `<plan-base>-external-<n>.md`.
- **One owner per file name.** With these four report forms (`validation-claude`, `validation-codex`, `validation`, `codex-raw`), a file name belongs to at most one plan. Proof: a file of plan `S` that also fits a longer plan `S-X` needs a rest of `S` equal to `X-` plus a rest of `S-X`. Every rest starts with `validation-` or `codex-raw-`, and no rest equals `X-validation-…` or `X-codex-raw-…` for any `X` (the only rests that start with another word plus `-validation-` would be `validation-validation-…`, which is not a form). Example: with plans `ana-plan` and `ana-plan-validation`, `ana-plan-validation-codex-1.md` is the new Codex report of `ana-plan`, and `ana-plan-validation-codex-raw-1.md` is the old Codex report of `ana-plan-validation`. So the readers need no list of plan names.
- **Round number `<n>`** (one rule for every writer). The rule sentence, word for word in each writer: "`<n>` is 1 plus the highest number at the end of any validator report or decision log of this plan in `.plans/.validations/` (`<plan-base>-validation-claude-<n>.md`, `-validation-codex-<n>.md`, `-validation-round-<n>.md`, and the older `-validation-<n>.md`, `-codex-raw-<n>.md`, `-round-<n>.md`), or 1 when there is none." `/skill-auto-validate-plan` takes it once at the start of each round (step a, before the snapshot) and uses it for the snapshot, the Codex report, the Claude report and the decision log of that round. It gives `<n>` to the `plan-validator` agent in the briefing. The agent alone (`/skill-validate-plan`) takes `<n>` with the same rule. So a new run never overwrites an earlier round. The snapshot `-pre-round-<n>` does not count: a round that stopped before its reports reuses its number and overwrites only its own gitignored snapshot.
- **Rounds of one run `k`.** `/skill-auto-validate-plan` counts the rounds of this run with `k` = 1 … 4, apart from `<n>`. The limit, the stop rules of step d and the "previous round" diff of step a use `k`: the diff compares this round's snapshot with the snapshot of round `k-1` of this run, and the first round of a run (`k` = 1) has no diff.
- One validation of a plan runs at a time, as today: a second run at the same time would also edit the same plan file. The rule reserves no number.
- **Count rule** (both readers): a round is one `<n>`. The dashboard counts the distinct `<n>` of all validator reports of the plan. `plan-lanes.mjs` gives `validation: { claude, codex, rounds }`: the distinct `<n>` per validator, and `rounds`, the distinct `<n>` of both together (the number the dashboard shows). An old and a new report with the same validator and `<n>` count once. Old reports from two runs under the old rules can have Claude and Codex numbers that do not line up; the count then shows more rounds than really ran. The plan accepts that for old reports (decision 1A).

## Breaking changes

- The dashboard's `validations` number per plan (read by `apps/dashboard/page/app.js`: the "validated ×N" chip, the ready/backlog column and the "not validated" chip) now counts rounds, not files. Zero stays zero, so the column logic does not change.
- `plan-lanes.mjs` `validation.codex` now counts the Codex reports that it missed before, both counts are distinct rounds, and the field gets a third key `rounds` (added; no consumer reads a fixed key list). Consumers: the lanes row chip in `apps/dashboard/page/app.js` ("✓ validated N× claude · M× codex") shows the Codex number once the project's own `.claude/scripts/plan-lanes.mjs` is rendered again (the dashboard runs the project's copy); the `score` now adds `rounds * 50` instead of `(claude + codex) * 50`, so a plan validated by both validators no longer scores twice per round, and the order of `recommendedBatch` can change; the text digest line becomes `validation=<c>c/<x>x/<r>r`, which `/plans-parallel` reads (step 6b).
- `skills/bootstrap-project/references/contracts.md`, the `plan-lanes` JSON shape: `validation: { claude, codex, rounds }`.
- A second run of `/skill-auto-validate-plan` on the same plan now writes rounds `<highest>+1 …` and no longer starts at 1.
- Other bootstrapped projects keep the old skill text until the owner runs `/bootstrap-project --upgrade` there and says yes to the changed files. Their old and new reports both count.
- Anyone who opens `.plans/.validations/` by hand sees two name styles: the old reports stay (decision 1A).
