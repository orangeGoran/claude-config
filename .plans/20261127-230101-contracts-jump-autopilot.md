# Plan: Contracts jump autopilot, worktree-aware step gate and `--max-rounds`

- **Base**: main
- **Parent**: .plans/20261123-100855-orchestrator-parent.md
- **Waits for**: claude-config plan 20261127-195706-groups-ledger-checklist merged

## Goal

The owner no longer types "api PR #N merged, check the contracts". When the contracts submodule of a project falls behind its upstream, the dashboard says so once, and the ☑ Checklist of the project's group proposes one jump after the open upstream PRs. One click on Confirm writes one jump plan that starts by itself when all those PRs are merged. This is phase 5 ("Contracts autopilot rule and template fixes") of the orchestrator parent plan.

The plan also ships three template parts of phase 5: the jump-plan rule as an optional bootstrap module (off by default), a step gate (`workflow-guard.sh`) that reads the worktree the commit runs in, and an optional `--max-rounds <1-4>` argument for `/skill-auto-validate-plan`.

Example, end to end:
1. The registry has `acme-api` (root `~/Workspace/acme/api`, origin `https://github.com/acme/api.git`) and `acme-web` with `"group": "acme-product"` and `"watchSubmodules": ["contracts"]`. `acme-web/contracts` is a submodule whose origin is `https://github.com/acme/api.git`, so its upstream project is `acme-api`. `acme-web` pins `contracts` at `c1` on `origin/main`.
2. A commit `c2` lands on `acme/api` `main`. On the next watcher tick (at most 60 s), the dashboard fetches the submodule, sees that `c1` is behind `c2`, writes the event `submodule-behind` (`path: contracts`, `pin: c1`, `tip: c2`) and shows one notification "acme-web · submodule behind". A click opens the checklist of `acme-product`.
3. `acme-api` has open PRs #41, #42 and #43 on `main`, and a draft #44. The checklist shows the card "Contracts jump · acme-web · contracts": "Recommended: one jump after #41, #42, #43 (#44 is a draft, left out)", one ticked checkbox per PR and **Confirm**.
4. The owner unticks #43 and clicks Confirm. The server writes `acme-web/.plans/20261128-091500-contracts-jump-contracts.md` with `- **Contracts jump**: contracts`, `- **Waits for**: acme-api PR #41 merged` and `- **Waits for**: acme-api PR #42 merged`, and answers with the commands that push the plan to `origin/main`. The card now says "A jump plan is on its way" with the plan link, and offers no new recommendation.
5. The owner pushes the plan. When #41 and #42 are merged, the existing watcher starts the plan (phase 1). The run moves `contracts` to the newest commit of `origin/main` at run time, makes the code build with the new types, and opens one draft PR.

## Decisions taken for the owner

The owner was not available while this plan was written. Each item is the safest default that fits the decisions above.

- D1 — The upstream project of a watched submodule is the registered project whose `origin` remote is the same repo as the submodule's `origin` (normalized by `repoKey()`: GitHub `https`/`ssh` forms, `.git` and case do not count). Reason: decision 3A says "the registered project whose repo the submodule points to"; a third repo is not guessed. Without such a project, the card offers only "jump now".
- D2 — An upstream PR "changes the contracts files" when it is open, not a draft, and its base is the branch that the submodule follows. Reason: the submodule repo holds only the contracts, so each PR to its branch changes them; no per-file GitHub call per tick.
- D3 — The branch that the submodule follows is its `branch = <name>` line in `.gitmodules`, else the submodule's `origin/HEAD`. A `branch = .` means the project's base branch. Neither → the card shows the error "cannot find the upstream branch". Reason: these are git's own rules for `git submodule update --remote`.
- D4 — The base branch of the downstream project is the `BASE_BRANCH="<x>"` line of its `.claude/scripts/auto-pipeline.sh` (the branch its runs start from). A project without the script gets the error "needs .claude/scripts/auto-pipeline.sh". Reason: the registry has no base field, and only pipeline projects can start a plan by itself.
- D5 — The card recommends a batch also when the pin equals the upstream tip and the upstream has open PRs (a jump planned ahead); "jump now" only when the pin is behind and no PR is open. Reason: the owner can arrange the jump before the merges, which is the batch model of 2026-11-22.
- D6 — The first check of a watched submodule counts: a pin that is behind already gives one event. Reason: the owner turns the watch on to learn this.
- D7 — The watcher sorts the pin against the tip as `equal`, `behind` (the pin is an ancestor of the tip), `ahead` (the tip is an ancestor of the pin) or `diverged`. An event comes only for `behind`. For `ahead` and `diverged` the card shows `diverged` and offers no jump, not even a batch; the jump plan checks the ancestry again just before its checkout and stops when it fails. Reason: a jump never moves a pin backwards or onto another line.
- D8 — The server never commits or pushes the jump plan. The Confirm answer gives the three commands (add, commit, push), and the card shows "pushed ✓/✗" for the jump plan. Reason: AGENTS.md "Never push `main` from an automated run"; the launcher needs the plan on `origin/<base>`.
- D9 — A "jump now" plan has no `Waits for:` line, so it does not start by itself: the owner launches it after the push. Reason: `canAutoLaunch()` starts only plans with at least one `Waits for:` line; a line that is always true would be a new condition kind.
- D10 — The jump plan text is generic (default headings Goal, Context, Steps, Tests, How to verify), types-only, and comes from the pure function `jumpPlanText()`. When the repo has `.claude/skills/contracts-jump/SKILL.md` (the new module), the plan says to follow it. The plan text says that its `## Steps`, `## Tests` and `## How to verify` are the default headings, and the module skill says to read them as the project's own step, test and verify headings (`rules.planSections`). Reason: one tested text for every project; the module carries the project rule.
- D11 — The card is only in the ☑ Checklist, so only grouped projects show it. A watched project without a group still gets the event and the notification. Reason: plan 2a, decision 1A: no group, no checklist.
- D12 — The new module is off by default through a `DEFAULT_OFF` list in `render.mjs`: `moduleOn()` is true for `contracts-jump` only when `modules["contracts-jump"]` is `true`. Reason: every other module is on unless turned off; decision 5 says off by default.
- D13 — Step gate: the commit's repo is the same repo when `git rev-parse --git-common-dir` (absolute, real path) is the same. The commit's folder is found in shell order: each `cd <folder>` before the commit in the same command, then each `-C <folder>` of the commit, from the hook input's `cwd`. A `cd` whose folder cannot be read (no word, `-`, a variable, a glob), or two commits with different folders in one command, make the folder unknown, and the guard then blocks the commit with a message (never unchecked, never checked against another worktree's exemptions). Branch, index and `.plans/` are read in that folder's top folder (the worktree). Reason: a linked worktree is the same repo with its own branch and index.
- D14 — `--max-rounds` with a value that is not 1, 2, 3 or 4 → the skill says so in one line and uses 4. Reason: a typo must not skip validation.
- D15 — The notification of `submodule-behind` opens `?checklist=<group>`; the page opens the checklist of that group (like `?scout=1`). Reason: the card is where the owner acts. A group that no longer exists falls back to the first group (the 2a `ckPick()` rule).
- D16 — At most 8 watched paths per project; a bad path is dropped with a Settings warning (the `group` pattern of 2a). Reason: each path costs a `git fetch` per minute.
- D17 — A checkbox the owner unticks stays unticked across the checklist's repaints, for the open page only (not stored). Reason: the drawer repaints on each changed answer; a reload shows the recommendation again.
- D18 — The jump plan's slug is `<YYYYMMDD-HHMMSS local>-contracts-jump-<path slug>`, written with `flag: 'wx'` (never overwrites). Reason: the AGENTS.md plan name rule.
- D19 — The open upstream PRs are read in full once per tick for each watched path that has an upstream (`gh api …/pulls?state=open&base=<branch>`, at most 5 pages of 100), not from the dashboard's 200-PR cache. Until the first read, the card is `unchecked`, never "jump now". Reason: the cache keeps one PR per branch and only the newest 200 PRs.
- D20 — A jump plan that is not on `origin/<base>` when its PRs merge does not start: the launcher prints `SKIP: plan not on …` and the watcher does not try again (phase 1 rule). The card keeps "not on origin yet ✗" with the push commands, and the docs say: push it, then launch it by hand. A jump plan whose PR was closed, or that waits for a PR that was closed, blocks new recommendations until the owner archives it; the card says so. Reason: no new retry or recovery logic in the watcher in this plan.
- D21 — Confirm refuses a project whose registry `plansDir` is not `<root>/.plans`. Reason: `auto-pipeline.sh` reads plans only from `$REPO/.plans` on `origin/<base>`, so a plan elsewhere could never start.
- D22 — An open jump PR blocks a new recommendation also after its plan file was archived: the watcher reads the downstream project's open PRs in full and looks for `auto/*-contracts-jump-<path>` heads; when it cannot read them, the card is blocked, not open. Reason: a second jump while one is open is the side effect decision 3A forbids.

## Hard rules

No Shipyard change, so no `npm run build-app`.

## Contracts

- **Registry entry:** new optional field `watchSubmodules`: an array of submodule paths. Each path matches `safeSubPath()`: 1–200 characters of `A-Z a-z 0-9 _ . / -`, does not start with `/` or `-`, and has no `.`, `..` or empty segment (`.contracts` is good). Each such path is also a good `submodule <path> contains <sha>` path for `parseWaitsFor()`, whose rule is wider. At most 8, no repeats. `cleanEntry()` accepts an array or a string split on commas and spaces (the Settings input), stores an array, and leaves the key out when no path is good. `resolveProject()` gives `watchSubmodules: []` for a missing or bad value.
- **`<stateDir>/watch.json`:** new key `subs`: `{ "<path>": { base, branch, pin, tip, relation, behind, upstream, remote, prs, jumpPrs, checkedAt, error, notedTip } }` (`pin`, `tip`, `notedTip`: 40-hex or null; `relation`: `equal`, `behind`, `ahead`, `diverged` or null; `upstream`: a registry name or null; `prs`: `{ error, rows }` of the open upstream PRs on `branch`, or null; `jumpPrs`: `{ error, rows }` of the open jump PRs of the project itself; `error`: a short redacted reason or null).
- **Events** (`events.jsonl`, `GET /api/events`): `submodule-behind` with `path`, `branch`, `pin`, `tip`, `upstream`; `submodule-error` with `path`, `reason`.
- **`GET /api/ledger`** (additive): `contracts`: one item per watched path of each group project, sorted by project and path:
  ```json
  { "project": "acme-web", "path": "contracts", "branch": "main", "pin": "<40 hex>", "tip": "<40 hex>",
    "relation": "behind", "behind": true, "upstream": "acme-api", "checkedAt": "2026-11-28T09:14:00.000Z", "error": null,
    "state": "batch",
    "recommended": [{ "number": 41, "title": "Add invoice fields", "url": "https://example.test/pull/41" }],
    "drafts": [{ "number": 44, "title": "WIP", "url": "https://example.test/pull/44" }],
    "blockers": [] }
  ```
  - `state` is one of `unchecked`, `error`, `diverged`, `blocked`, `batch`, `now`, `up-to-date` (rules in `recommendJump()`, step 2).
  - `blockers`: `[{ slug, archived, pr: { number, state, url } | null, pushed, push }]`, or `{ slug: null, error }` when the open jump PRs cannot be read. `pushed` is true when `origin/<base>` has the plan file; `push` is the text of the three push commands.
- **`POST /api/contracts/jump`** with `{ project, path, prs: [41, 42] }` → 200 `{ ok: true, slug, file, output }`; 200 `{ ok: false, output }` when the card does not allow it (blocked, unchecked, error, diverged, nothing to jump, no `BASE_BRANCH`, a PR that is not in `recommended`, the file exists); 400 `{ error: 'bad project' }` for an unknown project; 400 `{ error: 'not a watched submodule' }` for a path that is not in `watchSubmodules`; 400 `{ error: 'bad prs' }` when `prs` is not an array of at most 50 whole numbers from 1 to 9999999.
- **The jump plan file** (`jumpPlanText()`, step 3): header lines `- **Base**: <base>`, `- **Contracts jump**: <path>` (new, read by `parseJumpLine()`), and one `- **Waits for**: <upstream> PR #<n> merged` per chosen PR (the existing phase 1 condition).
- **Bootstrap:** new module key `modules["contracts-jump"]` (default off); new template switch `MOD_CONTRACTS_JUMP`; new rendered skill `.claude/skills/contracts-jump/SKILL.md`; `skill-auto-validate-plan` `argument-hint` becomes `"[plan file] [--max-rounds <1-4>]"`.
- Consumers: the page (`renderChecklist()`), later the phase 3 conductor (`recommendJump()`, `GET /api/ledger`, `GET /api/events`), the dashboard's own `parseWaitsFor()` (reads the jump plan), and `/bootstrap-project` (`render.mjs`, `verify.mjs` through `moduleOn()`).

### Harness constraints

- The end-to-end harness has no browser: the card's checkboxes and the Confirm click are checked in the browser test; the HTML in the page-function case.
- No real GitHub: the upstream PR list comes from the fake `gh` (`FAKE_GH_DIR/<repo>/list.json`; the fake ignores `state=open` and `base=`, so the lists hold MERGED and other-base rows on purpose and `recommendJump()` filters them), and the repos are local bare repos, so `repoKey()` matches local paths in the tests and GitHub URLs only in the unit tests.
- The real macOS notification is not shown: the fake notifier logs its arguments (`NOTIFY_LOG`).
- The guard's `common()` follows the server's `gitCommonDir()` pattern (`git rev-parse --git-common-dir`, resolved against the folder), which works on every git version; no `--path-format`.
- The guard tests pass the hook input as JSON with `tool_input.command` and a `cwd` field, the shape Claude Code sends to a PreToolUse hook; they cannot show that a live session's `cwd` follows a `cd` of an earlier Bash call. The guard falls back to `process.cwd()` when `cwd` is missing.
- The owner-by-hand copies (step 18) are not tested by the run; **How to verify** has the `grep` checks and the `render.mjs --upgrade` status check the owner runs after the copy.
