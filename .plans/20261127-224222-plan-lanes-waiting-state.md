# Plan: plan-lanes shows plans that wait for a condition

- **Base**: main
- **Parent**: `.plans/20261123-100855-orchestrator-parent.md`

## Goal

A plan with a `- **Waits for**:` line that is not met yet must not show as "ready to launch". Today `plan-lanes.mjs` ignores that line, so `/plans-parallel` and the dashboard's "⚡ suggested launch batch" can recommend a plan that waits for "acme-api PR #12 merged". The owner then launches it by hand, before the work it depends on is merged.

After this plan, the `plan-lanes.mjs` template:

- reads the `Waits for:` lines of each plan header,
- asks the dashboard watcher's saved result (`watch.json`) whether they are met, through one function `waitStateOf()`,
- keeps a waiting plan in its lane, but never puts it in the recommended batch,
- lists the waiting plans with their conditions, and with the age of the watcher's last check when that check is old or missing,
- warns on a batch plan that shares files with a waiting plan, because the watcher can start the waiting plan by itself while the batch plan runs,
- finds the dashboard state folder of its repo by the registry entry whose `root` is the repo, not by the folder name (the dashboard uses the registry `name`).

This is phase 2b of the parent plan ("`plan-lanes.mjs` waiting state").

## Context

- Parent plan sections: "Phases" → 2b; "Proposed design" → 2 (follow-ups on events); "What the dashboard already has".
- Decisions taken for this plan (owner, 2026-11-27):
  - 1A+ — one judge of "met": the dashboard watcher. plan-lanes reads `watch.json` (`met[slug]`, `checkedAt`) through one function `waitStateOf()` and never checks a condition itself (no `gh`, no network, no read of another project). A plan that the watcher has not seen met stays "not met" (the safe side), also when `watch.json` is missing or its last check is old, and the output says how old the last check is. A stored `met[slug] === true` counts as met at any age: the watcher writes it only after all conditions held, and the three conditions do not go back (a merged PR stays merged, a merged plan stays merged, a pushed submodule commit stays in the history). A later change (a result per condition, a state on a server) changes only `waitStateOf()`. This is the pattern of Kubernetes status conditions, the Airflow triggerer and the Mergify `Depends-On` status: one part checks, every other part reads its result.
  - 2A — a ready plan that shares files with a waiting plan stays in the batch, with a `!!` warning line and a `sharesWithWaiting` list in the JSON. The lane is not held.
- Open decisions this plan does not take: none of the parent plan's open decisions (priority columns: phase 3; questions parent issue: phase 4).
- Known limits, written into the parent plan as watcher follow-ups (a later plan that changes `apps/dashboard/server.mjs`, after 2a):
  - The watcher's `canAutoLaunch()` (`apps/dashboard/watch.mjs`) does not check lanes, so it can start a waiting plan while a run that edits the same files is active.
  - The watcher sets `met[slug] = true` once and never sets it back (`watchProject()` step "5. waits"). When the owner changes a met plan's `Waits for:` line, `met` stays true. It keeps the result per condition only in memory (`waitStatus`).
  - `checkedAt` moves only when the watcher's PR read works (`watchProject()` step 1, `next.checkedAt = tickAt`), but the waits are checked on every tick. So a fresh `checkedAt` does not prove that the current conditions were checked, and an old one can come from a failed PR read while the waits were checked. plan-lanes uses it only for the age note.
  - A plan that the owner launched by hand before its condition was met is never checked again (`watchProject()`: `if (next.launched[p.slug] || p.run) continue;`), so `met` never becomes true for it. plan-lanes therefore lists as waiting only plans that do not run and did not ship (step 6).
- A plan that the watcher has seen met but not started yet (for example, the limit of 4 runs is full) is in the batch, and no `sharesWithWaiting` line names it, though the watcher can start it on its next tick. This follows from 1A+ (met is met); the watcher's lane guard in the later plan covers it.
- The age limit `WAIT_STALE_MS` (10 minutes) is fixed. It does not follow `DASH_WATCH_MS`, which only the dashboard process reads.
- Owner decision (validation round 1, answer A): the dashboard's "⚡ suggested launch batch" drawer does not show `sharesWithWaiting` in this plan (`laneRowHtml()` reads only `slug`, `file`, `validation`, `areas`). The drawer warning goes to the later watcher plan, together with the watcher's lane guard. Until then, the `!!` line is only in the `/plans-parallel` text and the JSON.
- The dashboard drawer shows `schedulableCount` as "N ready". A waiting plan stays schedulable (it is in a lane), so that number still counts it. The drawer is in `apps/dashboard/page/app.js`, which plan 2a changes; a later dashboard plan can show `waitingCount`.
- Name of the state folder: the dashboard uses the registry `name` (`resolveProject()` → `stateDir = path.join(CENTRAL, 'state', p.name)`), and `/bootstrap-project` registers `project.name`, which can differ from the folder name (`register.mjs`: `entry = { name: p.project.name, …, root }`). The template takes the folder name today (`CENTRAL_STATE … path.basename(REPO)`), so it can read the wrong folder for `plan-meta.json`, `runs.json` and the new `watch.json`. This plan adds `projectName()`: the `name` of the registry entry (`~/.claude/pipeline-projects.json`, `projects[]`) whose `root` (with `~` expanded) resolves to `REPO`, else the folder name as today. `register.mjs` refuses a second entry with the same root, so at most one entry matches. Inside a run worktree no entry matches, and the folder name stays the fallback, as today.

- Mirror:
  - `watch.mjs` `parseWaitsFor()` (header = text before the first `## ` line, ``` fences skipped, backticks removed) → template `waitsForLines(text)` (returns only the condition texts; the template is copied into other repos and cannot import the dashboard).
  - `META_FILE` + `readJson()` → `WATCH_FILE = path.join(CENTRAL_STATE, 'watch.json')` + `readJson()`.
  - `register.mjs` same-root check (`path.resolve(untilde(x.root || '')) === repo`) → `projectName()` (registry entry whose expanded, real `root` is `REPO`).
  - `runState()` / `occupied()` (a running or shipped plan is not schedulable) → the same states keep a plan out of `waiting`.
  - `blockedByActiveRun` (shared `hard` files with each active run) → `sharesWithWaiting` (shared `hard` files with each waiting plan).
  - The `if (p.hasUncommittedEdits) continue;` skip in the batch loop → `if (p.waits && !p.waits.met) continue;`.
  - The `!!` line of `blockedByActiveRun` in the text output → a `!!` line for `sharesWithWaiting`.
  - The `IN FLIGHT / AWAITING REVIEW` text section → a `WAITING` text section.
- Deviations:
  - `waitsForLines()` does not sort conditions into kinds (`pr`, `plan`, `submodule`, `bad`) — plan-lanes does not check them (1A+), so it needs only the text.
  - Staleness: plan-lanes marks a result older than 10 minutes as stale (`WAIT_STALE_MS = 10 * 60 * 1000`, ten watcher ticks of the default `WATCH_MS` 60 s). The dashboard has no such mark — it is the checker itself.
  - `projectName()` compares real paths (`realpathSync`), not only `path.resolve`: Node starts the script by its real path, so `REPO` is `/private/var/…` on macOS when the registry says `/var/…`.
