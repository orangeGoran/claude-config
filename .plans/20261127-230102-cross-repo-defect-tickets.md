# Plan: Tickets for defects of another repo

- **Base**: main

## Goal

When a review in an unattended run (verify, the browser test, the decision sheet's Codex review) finds a defect whose cause is in another repo of the same group, the run does not work around it. In "to PR" mode it opens a GitHub issue in that repo by itself and links it in the PR body. When the run cannot tell which repo is at fault, it opens a triage issue in its own repo, and the ☑ Checklist and a macOS notification bring that issue to the owner. This is plan 2 of the pipeline diet parent plan ("Tickets for defects of another repo"): the owner no longer writes "make a ticket for the backend" after each PR.

Example, end to end:
1. The registry has `acme-web` (repo `acme/web`) and `acme-api` (repo `acme/api`), both with `"group": "acme-product"`.
2. The owner launches the `acme-web` plan `20261128-090000-invoice-screen` in "to PR" mode on the dashboard. `runLauncher()` starts `auto-pipeline.sh` with `DASH_RELATED_REPOS={"group":"acme-product","self":"acme/web","related":[{"repo":"acme/api","project":"acme-api","short":"api"}]}`.
3. The script writes `.plans/auto-runs/20261128-090000-invoice-screen-related.json` and starts `/skill-auto-pipeline 20261128-090000-invoice-screen.md --report=… --stop-after=pr --base=main --related=<that file>`.
4. The browser test sees `GET /v1/invoices/7` answer `"total": null` for a paid invoice. The fix belongs in `acme/api`. The run writes `D1. acme/api — GET /v1/invoices/7 gives total null for a paid invoice — source: browser test — evidence: … — ticket: open` under `## Defects in other repos` in the report, and does not change the screen to hide it.
5. The run opens draft PR `acme/web#12`. Then it runs `gh label create from-pipeline --repo acme/api …` ("already exists" is fine), writes the ticket body, and runs `gh issue create --repo acme/api --title "Invoice total is null for a paid invoice" --label from-pipeline --body-file …`. The body has the evidence and `Source PR: https://github.com/acme/web/pull/12`.
6. The run adds `## Defects in other repos` with `D1 → https://github.com/acme/api/issues/88` to the PR body (`gh pr edit 12 --body-file …`).
7. A second finding could come from `acme/api` or from the shared contracts repo. The run opens `acme/web#89` with the labels `from-pipeline` and `needs-triage`, names both candidates, and links PR #12.
8. Within one watcher tick (60 s) the owner gets a notification "web · needs triage · #89". A click opens ☑ Checklist on `acme-product`. Its "Needs you now" box shows the row `acme-web · needs triage · #89 …`.
9. Later, `/skill-1-plan` in `acme-api` lists the open `from-pipeline` issues, merges #88 with a related open one into one plan, and writes `- **Tickets**: #88, #91`.

## Decisions taken for the owner

- **Transport of the list: an env variable, then a file in the run folder.** `runLauncher()` sets `DASH_RELATED_REPOS` (JSON) on the launcher process, as `launchGeneric()` sets `DASH_EXIT_FILE` and `PLAN_REPORT`; `auto-pipeline.sh` writes it to `.plans/auto-runs/<slug>-related.json` and adds `--related=<path>` to the prompt, as it passes `--report=<path>`. Reason: JSON in the prompt needs shell quoting, and the file survives a resume and can be read by the run (`Read(//<repo>/.plans/auto-runs/**)` is in the run overlay).
- **Resume.** A dashboard resume sets the variable again (the group can have changed): a valid value rewrites the file, an empty or bad value removes it. A resume by hand (variable unset) keeps the file of the launch. A launch with the variable unset removes an old file. Reason: a run keeps its list unless the dashboard says otherwise.
- **No role field.** Each related entry has `repo`, `project` and `short` only. Reason: the registry has no role field (`resolveProject()`), and the project name and the repo name tell the run enough (`acme-api`).
- **Who is related.** The other registry projects with the same `group` and a GitHub `issuesUrl`, one entry per repo, without the run's own repo. No such project, no group, or no GitHub remote of its own → no list. Reason: a ticket needs a GitHub repo; a second registry entry on the same repo is not "another repo".
- **The tickets are opened after the PR exists, by `skill-auto-pipeline`, not by `skill-5-ship`.** Reason: each ticket body needs the PR link, and `skill-5-ship` also runs interactively, where this rule does not apply.
- **The label is made without `--force`.** `gh label create … ` with an "already exists" error counts as done. Reason: `--force` would overwrite a color or text the repo owner chose.
- **A failed `gh` write never blocks the run.** The `D<n>` line gets `ticket: failed (<reason>)`, and the PR body says it. Reason: the PR is the main result; a missing right in another repo must not hide it.
- **Allow rules.** `Bash(gh issue create*)`, `Bash(gh label create*)` and the recovery read `Bash(gh api repos/*/issues -X GET -f labels=from-pipeline*)` go only into the "to PR" overlay of `write_run_settings()`; `Bash(gh issue list*)` (read only) goes into the shared allow list of `render.mjs`, for `skill-1-plan`. `verify.mjs` fails when a shared allow list has an issue or label write rule. Reason: the same rule as push and PR writes (lesson 1): network writes only in the mode that the owner chose for them.
- **A cross-repo defect is not an owner question.** It never makes `NEEDS DECISION`, it is not a verify "deferred" item, and the decision sheet does not ask about it; the sheet gets one `ℹ️ Defects in other repos: <n>` line. Reason: the owner already decided (4B) what happens to it.
- **Triage poll scope.** The watcher reads open `needs-triage` issues only for projects with a `group` and a GitHub remote, with one REST call per project per tick. The first read of a project is a baseline with no notification (as the PR list's first read). Reason: no extra GitHub calls for projects without a group, and no burst of notifications for old issues after an upgrade.
- **Notification click.** It opens `?checklist=<group>&issue=<n>`, through the `?checklist=<group>` opener that the sibling plan adds (the extra `issue` makes the `-group` of each notification unique). Reason: one opener for every checklist notification.
- **No duplicate after a crash.** Before `gh issue create`, the run writes the Timeline line `ticket creating: D<n> <repo>`. A resumed run that finds this line without `ticket opened: D<n>` first runs `gh api repos/<recorded repo>/issues -X GET -f labels=from-pipeline -f state=all -f sort=created -f direction=desc -f per_page=100 --jq '.[] | {url: .html_url, body}'` (the REST list, not the search index, so a new issue shows at once) and takes the issue whose body has the exact line `<!-- from-pipeline source-pr=<PR url> defect=D<n> -->` (a link to an issue that exists, also when that repo has left the group since). No such issue and fewer than 100 rows → it creates one in the target of now (item 7.5.2). 100 rows without a hit, or a failed call → `ticket: failed (recovery: <reason>)`, no create. Reason: this is not the 8A duplicate check (other runs' tickets), only the recovery of the run's own write.
- **Resume into "to PR" mode.** Item 7.5 also takes `ticket: would open in <repo>` lines. After the crash recovery, it checks each target of a new create again against the `--related` file of now: a target that is no longer in it becomes `unclear` (a triage ticket in the own repo); no file now → `none (no list)`. Reason: the list of now decides, and no ticket goes to a repo that left the group.
- **The PR body section is replaced, not appended.** Item 7.5 reads the live body (`gh pr view <n> --json body --jq .body`), replaces the block between `<!-- defects-other-repos:start -->` and `<!-- defects-other-repos:end -->` (or appends it once), and writes it back with `gh pr edit`. Reason: a resume or a second pass must not add the section twice, and edits made after ship stay.
- **Redaction.** Ticket titles, ticket bodies, `D<n>` lines and `failed (<reason>)` texts hold no header values except `Content-Type`, no cookie, token, key or password value, no URL query string, and no real person's name or address; such a value is written as `<redacted>`, and an error text is cut to 160 characters. Reason: the text goes to another repo and to the PR.
- **A label that cannot be made stops that ticket.** An error other than "already exists" → `ticket: failed (label: <reason>)`, and no issue is created. Reason: a ticket without `from-pipeline` breaks the 8A search.
- **Two registry entries on one repo.** The watcher reads the triage issues of a repo once, through the first grouped registry entry of that repo; `ledgerState()` lists each `repo#number` once. A project that loses its group gets `triage: null` again, so a later group starts with a new baseline. Reason: no double rows, no double notifications, no burst after a regroup.
- **`skill-1-plan` leaves `needs-triage` tickets alone.** It skips open `from-pipeline` issues that also have `needs-triage` and lists them in one line. Reason: they wait for the owner or the conductor to pick a repo.
- **The ticket allow rules are not limited to a repo.** `Bash(gh issue create*)` permits any `--repo`; the skill text limits the target to `self` and the `--related` repos. Reason: a rule cannot read the run file; the "to PR" mode is the owner's permission for network writes.
- **The triage rows go into the 2a "Needs you now" box.** The box shows when it has a plan, a triage issue or a triage read error. Reason: one place for what needs the owner, and no empty box.
- **Only pipeline triage tickets.** The watcher reads issues with both labels `from-pipeline` and `needs-triage`. Reason: many repos use `needs-triage` for ordinary issues, and those must not look like pipeline tickets.
- **One cache per repo.** The triage cache is keyed by the lower-case repo, so all registry entries on one repo share one read, and the watcher refreshes each repo once per tick. Reason: one call per repo, and every group of that repo sees the same rows.
- **Recovery never guesses.** The recovery list uses the REST issues list through `gh api` (not the search index, which `gh issue list` with filters can use, so a new issue shows at once) and takes only an issue whose body has the exact marker; a failed list leaves `ticket: failed (recovery: <reason>)` and creates nothing. Reason: a duplicate and a wrong link are both worse than a retry by the owner.
- **Tickets land after `PR OPEN`.** Item 7.5 runs after `skill-5-ship` set `PR OPEN`, so for a few minutes the draft PR has no defects block. Reason: the ticket needs the PR link; the PR is a draft and the owner reads it later.
- **`skill-1-plan` searches in every project.** The `from-pipeline` step is not behind `HAS_TICKETS`. Without `HAS_TICKETS`, the plan header gets a `- **Tickets**:` line only when it names `from-pipeline` issues. Reason: a run in any grouped project can open such issues, and the 2a chain reads the `Tickets:` line.
- **Repo name rule.** `self` and each related `repo` must match `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`; the script drops the whole list when one value does not match. Reason: the value goes into `gh --repo`; a partial list could send a ticket to the wrong repo.
- **One ticket path.** Item 7.5 "Tickets" is the one path for every issue a run opens. A later plan of `.plans/20261127-233245-hands-off-pipeline-parent.md` adds the policy routing of `.claude/decision-policy.md` to this item (a target `self` with the project's backend label, an assignee, a board and a Status column); it adds no second ticket path. Reason: one place to change when the PO channel of orchestrator phase 4 replaces the transport.

## Contracts

- **Run report Timeline lines** `ticket creating: D<n> <repo>` and `ticket opened: D<n> <url>` (re-run detection and crash recovery), `pr body: defects section written` / `pr body: defects section not written (<reason>)`, and `Would open a ticket in <repo>: <one line>` (verify and commit modes).
- **GitHub labels** `from-pipeline` (every ticket) and `needs-triage` (a ticket whose owner repo is unclear). **Ticket body** ends with `Source PR: <url>` and the hidden line `<!-- from-pipeline source-pr=<url> defect=D<n> -->`.
- **PR body block** between `<!-- defects-other-repos:start -->` and `<!-- defects-other-repos:end -->` (at the end of the body, replaced on each pass): `## Defects in other repos`, one line per `D<n>` with its ticket link or its "no ticket" reason.
- **`GET /api/ledger`** (additive): `triage: { items: [{ project, repo, number, title, url, createdAt }], errors: [{ project, error }], full }`, items sorted by `createdAt`, newest first. Consumers: `checklistHtml()`; later the phase 3 conductor.

- **`watch.json`** (additive): `triage`: `null` (not read yet) or the list of open `needs-triage` issue numbers of the last good read.
- **Page URL:** the sibling plan's `?checklist=<group>` opener; this plan's notification adds `&issue=<n>`, which the page ignores.

## Breaking changes

- `/api/ledger`, `events.jsonl`, `watch.json`: additive only. Consumers: `checklistHtml()` (reads named fields), `loadWatch()` (spreads the blank first, so an old file gets `triage: null`), the tests.
- `ticketKey()`: same results; it now calls `repoOf()`. Consumer: `buildChain()`; the 2a `ticketKey` unit cases prove it.
- `runLauncher()`: one more env variable for every pipeline launch and resume. An `auto-pipeline.sh` of an older template ignores it. A generic launcher (`launchGeneric()`) does not get it.
- `/skill-auto-pipeline` arguments: one optional argument. An older `auto-pipeline.sh` does not pass it; the skill then has no list and opens no ticket.
- Templates: a project gets the new text only after `/bootstrap-project --upgrade`. The shared allow list gets one read-only rule.
- `verify.mjs`: the new required check `issue-allow` fails a project whose `.claude/settings.json` allow list has a `gh issue` rule other than `view` and `list`, or any `gh label` rule, also one that came from `registry.extraAllow` in `bootstrap.json`. Such a project must remove that rule: the "to PR" overlay has the two rules a run needs. Consumers: `/bootstrap-project` verify and `--upgrade`.
- `checklistHtml()`: its signature does not change; it reads one more field.
