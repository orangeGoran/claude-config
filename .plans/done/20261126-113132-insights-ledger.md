# Plan: Insights ledger — one line per finished run, written by the dashboard

- **Base**: main
- **Parent**: `.plans/20261126-113131-plans-insights-parent.md`

## Goal

Keep one JSON line per finished pipeline run of every registered project in `~/.claude/pipeline-dashboard/insights.jsonl`: the cost, the tokens, the cost and minutes per phase, the mode, the outcome and the PR. The dashboard's event watcher adds the line of a new run by itself, and a migration command adds the lines of all old runs. This is plan 1 of the parent plan: the Insights page (plan 2) reads only this file.

Scope: projects with the auto-pipeline flavor (`<root>/.claude/scripts/auto-pipeline.sh` exists; runs in `<plansDir>/auto-runs/`). Generic-flavor projects (logs in `~/.claude/pipeline-dashboard/logs/<project>/`) are filtered out before the scan, by the same check as `resolveProject()` `hasPipeline`, and are not in the ledger.

A re-launch or resume of the same slug appends to the same run log (`auto-pipeline.sh` writes `>> "$4"`), so the ledger has one valid line per plan slug: the cost of all sessions of that plan.

## Hard rules

- **Restart after dashboard changes.** The plan changes `apps/dashboard/server.mjs` and adds `apps/dashboard/insights.mjs`, which the server imports. The run is in a worktree, so it does not restart. Its report lists under Open items: after the merge and `git pull` in the main checkout, run `pgrep -fl chat-relay.mjs`, and run `npm run restart` only when it shows that the live chats run under the relay.

- **Public repo: no private data.** No project names, paths or costs go into the repo. The ledger is in `~/.claude/`, outside the repo. Test fixtures use made-up names (`demo-api`, `demo-web`, `ledger-demo`) and made-up costs.
- **Global rules affect every project.** Not touched: no change to the root `CLAUDE.md` or `skills/`.
- **Never stop processes by name.** The watcher test uses the suite's shared server, which the suite stops with its `stop(child)` helper (by the child process). No new server is started. The CLI test runs a command that exits by itself.
- **Tests for logic changes.** New `apps/dashboard/test/insights.test.mjs` (unit tests of the module and the CLI), one end-to-end case in `apps/dashboard/test/watcher.test.mjs`, and one check in the existing copy test of `apps/dashboard/test/dashboard.test.mjs`. ## Contracts

- New file format: `~/.claude/pipeline-dashboard/insights.jsonl`, one JSON object per line, `v: 1`. Fields:
  - `v`, `project` (registry `name`), `slug`.
  - `src`: `{ logSize, logMtimeMs, reportSize, reportMtimeMs }` — the size and change time of the log and the report when the line was made (`reportSize` and `reportMtimeMs` are null when there is no report).
  - `launched`: the report's `- **Launched**:` value, parsed only when it matches `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}$` (local time), as an ISO string; else null.
  - `ended`: the log's change time as an ISO string.
  - `mode`: from the report's `- **Mode**:` line, or null.
  - `outcome`: the rule of `pipelineRunInfo()` and `parseReport()` in `server.mjs`, copied: the report's `- **Outcome**:` value, lower case, counts only when it is `running`, `needs-you` or `failed`. A `failed` whose status words do not give `failed` is stale (a chat fixed the run later) and is ignored. Without a value that counts, the status-word rule of `outcomeOf()` and `docs/plans-dashboard.md` ("Pipeline modes and run reports"): a status that starts with `VERIFIED`, `REVIEWED`, `COMMITTED`, `FINISHED` or `PR OPEN` gives `needs-you`; `BLOCKED`, `FAILED` or `ENDED` gives `failed`; any other status gives null. The status words match without regard to case, as in `outcomeOf()`. A dead run whose report still says `Outcome: running` (recorded after `staleMs`) keeps `running`; plan 2 shows such a run as "ended without a result". (One difference from `outcomeOf()`: the dashboard shows an unknown status as `running`; the ledger stores null, because a line is only written for a finished run, and a `CLEANED …` status must not read as `running`.)
  - `status`: the report's `## Status:` text, first 80 characters, or null.
  - `pr`: `{ number, url }` from the last `^PR: *(https://\S+/pull/(\d+))` line of the report (the regex of `sync_report_outcome` in `auto-pipeline.sh`), or null.
  - Usage reuse: when the log's `logSize` and `logMtimeMs` equal those of the previous valid line of the pair (only the report changed), the new line copies `results`, `cost`, `costSource`, `tokens`, `phases` and `minutes` from the previous line and does not parse the log again. So a report edit after the session transcripts are deleted keeps the phase split. When the log changed and its transcripts are gone, `cost` and `tokens` stay exact (they come from the log's result lines) and only the split across phases is less exact (the transcript tokens are missing).
  - Carry-over: when a new line of a pair has `outcome`, `mode`, `pr` or `launched` null and the previous valid line of the pair has a value, the new line keeps that value. A re-launch of the slug in verify mode therefore keeps the PR of the earlier run of the same plan; that PR still belongs to the plan, so this is intended. So `auto-pipeline.sh --cleanup` (it sets `## Status: CLEANED …` and deletes the Outcome line) keeps the finished outcome. A report that is already cleaned when the migration first sees it gives `outcome: null` and the `CLEANED …` status.
  - `results`: the number of result lines in the log (0: the run has no cost data).
  - `cost` (USD, rounded to cents) and `costSource` (`model_usage` or `total_cost_usd`): from `applyCosts()`; both null when the log has no cost. The ledger cost is always the `run-usage.mjs` total, so the two never differ. Known limit of that rule: when a log mixes result lines with model usage and lines with only `total_cost_usd`, `applyCosts()` sums the model-usage lines only. A change of that rule belongs in the `run-usage.mjs` template, not in this plan.
  - `tokens`: `{ input, cacheWrite, cacheRead, output }` summed over the result lines that have usage; null when no result line has usage (a log with only `total_cost_usd`).
  - `phases`: `{ <row name>: { cost, wall, active } }`. Rows with the same name in several sessions are added up. A value is null when one of the added values is null (the rule of `sumRows()` in `run-usage.mjs`). Costs are rounded to cents, minutes to 0.1.
  - `minutes`: the sum of the `wall` minutes of all rows except `unattributed`, or null when one of them is null.
- The valid line of a `project` + `slug` pair is its last line in the file. Only one writer at a time reads and appends: `syncLedger()` holds the lock file `insights.jsonl.lock` (next to the ledger) from the read of the ledger to the last append, so the last line is always made from the newest sources the writer saw.
- Consumers: only the new module now; plan 2 (`GET /api/insights`) later.

## Reference implementation

- Closest existing pattern: `apps/dashboard/watch.mjs` (helpers of the event watcher, imported by `server.mjs`, tested by `apps/dashboard/test/watcher.test.mjs`), and the event log `<stateDir>/events.jsonl` that the watcher appends to (`eventsFile()` in `server.mjs`), with `fence()` before each write. The CLI part mirrors `apps/scout/scout.mjs` (a module that the server imports and that also runs as a command: the `process.argv[1]` guard at its end).
- Files read end to end: `apps/dashboard/watch.mjs` (header and exported functions), `.claude/scripts/run-usage.mjs` (exported: `parseLog`, `loadSubagents`, `phaseRows`, `applyCosts`, `main`; internal, read for their rules only: `sumModelUsage`, `sumRows`), `server.mjs` sections "registry" (`loadRegistry`, `resolveProject`, `allProjects`), `pipelineLive()`, and "event watcher" (`STALE_RUN_MS`, `LOST_LOCK`, `holdsLock`, `fence`, `watchTick`, `startWatcher`), `scripts/docs-media.mjs` (`copyDashboard`), `apps/dashboard/test/watcher.test.mjs` helpers (`makeRepo`, `register`, `until`, `mainEnv`, the shared server in `before()`).
- Mirror:
  - `watch.mjs` helpers → `insights.mjs` `runRecord()`, `readLedger()`.
  - `run-usage.mjs` `main()` (read log → `parseLog` → `loadSubagents` → `phaseRows` → `applyCosts`, `projectsDir` default `~/.claude/projects`) → `insights.mjs` `runRecord()`, with the same calls, order and default.
  - `watchTick()` per-project loop and `fence()` before each write → one `syncLedger()` call after the loop, with `beforeWrite: fence`.
  - `pipelineLive()` → the server passes it as `isLive`; the CLI uses `insights.mjs` `pgrepLive()` with the same `pgrep -f '[s]kill-auto-pipeline <slug>\.md'` pattern.
  - The watcher lock (`linkLock()`, `lockState()`, `takeLock()`, `holdsLock()` in `server.mjs`) → the ledger lock `insights.jsonl.lock` in `insights.mjs` (`takeLedgerLock()`, `releaseLedgerLock()`), with the same algorithm: write `{ pid, cmd }` to a temp file and `linkSync` it to the lock (only one process gets it); when that fails, read the lock: an unreadable lock older than 10 s, a dead pid, or a pid whose `ps` command differs from `cmd` is stale; to replace a stale lock, `renameSync` it to `<lock>.stale.<pid>` (only one process can move it), check that the moved file has the stale pid (else link it back and give up), then `linkSync` again. Release: `unlinkSync` the lock only when it holds this process's pid. Signatures: `takeLedgerLock(lockFile)` returns `'ok'`, `'busy'` (another live process holds it) or `'no-ps'` (`ps` gave no command line for this process, as in `linkLock()`); `releaseLedgerLock(lockFile)` returns nothing. `syncLedger()` returns `{ busy: true, reason }` with that word when it is not `'ok'`, and the CLI prints "The dashboard is writing the ledger" only for `busy`, else "Cannot take the ledger lock: ps gave no command line".
  - `scout.mjs` CLI guard → `insights.mjs` `--migrate` command.
- Deviations:
  - `insights.mjs` does file I/O (`syncLedger`), unlike `watch.mjs` — the migration command and the watcher must share one function, so they cannot give different numbers.
  - The CLI reads the registry itself (`registryProjects()`) instead of `resolveProject()`, and has its own `pgrepLive()` — `resolveProject()` and `pipelineLive()` are not exported, and importing `server.mjs` starts the server.
  - `pgrepLive()` has no chat fallback (`pipelineLive()` also counts a `claude` process that is active in the run's worktree) — a chat does not write the run log, and when a chat changes the report later, the next sync makes a new line, so a line made early is corrected.
  - `insights.mjs` has its own copy of the outcome rule of `parseReport()`, `outcomeOf()` and `pipelineRunInfo()` — they are not exported and importing `server.mjs` starts the server. A test checks the same cases the dashboard uses. It differs in one point: an unknown status gives null, where `outcomeOf()` gives `running` (reason in Contracts).
  - The ledger lock has its own copy of the watcher-lock algorithm instead of a shared module — moving the watcher's lock code is outside this plan. One difference: the pid check treats `EPERM` from `process.kill(pid, 0)` as alive (only `ESRCH` means dead), where `pidAlive()` treats every error as dead; a live holder that this process cannot signal must not lose the lock.
  - `insights.mjs` imports `.claude/scripts/run-usage.mjs`, the copy that `skills/bootstrap-project/` renders from its template. A rename of that file or of its exports in the template breaks the server start; `npm test` shows it (the dashboard tests import the server).

First the usage reuse of the Contracts section: when `previous` is set and `src.logSize` and `src.logMtimeMs` equal `previous.src.logSize` and `previous.src.logMtimeMs`, it copies `results`, `cost`, `costSource`, `tokens`, `phases` and `minutes` from `previous`, does not parse the log (`logText` can be null then), and only builds the report fields. A missing report or field gives null. Doc comment in ASD-STE100.
3. In `insights.mjs`, add `export function readLedger(file = LEDGER)`: returns a `Map` of `project + '/' + slug` → the last line of that pair. It skips empty and unparsable lines and lines without `v`, `project`, `slug` and `src`. A missing file gives an empty map.
4. In `insights.mjs`, add `export function pgrepLive(slug)`: true when `pgrep -f '[s]kill-auto-pipeline <slug>\.md'` (the slug escaped as in `pipelineLive()`) exits 0. Uses `execFileSync`; every error (exit code 1, no `pgrep`, a timeout) gives false, as in `pipelineLive()`.
5. In `insights.mjs`, add `export async function syncLedger({ projects, file = LEDGER, projectsDir = path.join(os.homedir(), '.claude', 'projects'), limit = Infinity, maxBytes = Infinity, staleMs = DEFAULT_STALE_MS, now = Date.now(), isLive = (name, slug) => pgrepLive(slug), beforeWrite = () => {}, failed = new Map(), dryRun = false, readFile = readFileSync })`. `readFile` reads the logs and reports (the tests pass one that fails once). `projects` is `[{ name, autoRunsDir }]`; `isLive` gets the project name and the slug.
   - Unless `dryRun`, create the folder of `file` (`mkdirSync(..., { recursive: true })`), then take the lock `file + '.lock'` with `takeLedgerLock()` (the algorithm in Reference implementation). When another live process holds it, return `{ busy: true }` and write nothing. Release it with `releaseLedgerLock()` in a `finally`.
   - `failed` maps a pair to `{ src, at }`. An entry older than 10 minutes is removed, so a run whose read failed for a short time (a permission or I/O error) is tried again without a change of its files.
   - Read the ledger once with `readLedger(file)`. Skip a project whose `autoRunsDir` was seen before in this call (two registry entries with the same folder count once). For each project, in its own `try` (a missing or unreadable `autoRunsDir` is counted in `missing` and the next project goes on), for each `*.log` (skip names that start with `_`), inside a per-run `try` that holds every sub-step below (an error of `stat`, of a read or of `runRecord()` puts `{ src, at: now }` in `failed` when `src` is known, counts the log path in `errors`, and goes on with the next run; only an error of `beforeWrite()` goes up):
   - `stat` the log and `<slug>.md`, and make `src`. Skip it (`unchanged`) when the last ledger line of the pair has the same `src`, or when `failed` has the same `src` for the pair.
   - Read the report text: a report that does not exist (`ENOENT`) gives null; any other read error is an error of this run (retried later), not a missing report. Skip it (`live`) when `await isLive(name, slug)` is true, or when the report's Outcome is `running` or there is no report or no Outcome line, and the newest of the two change times is less than `staleMs` ago.
   - Stop the scan when `limit` lines are made or the log bytes read reach `maxBytes` (count the rest in `deferred`). The check runs before each log, so one log larger than `maxBytes` is still read when it is the first one; the budget counts log bytes only, not the subagent transcripts.
   - Read the log (skip the read when the log `src` equals the previous line's, see the usage reuse), `stat` the log and the report again; when `src` changed, skip it (`changing`) and try at the next call.
   - Call `runRecord()` with `previous` = the last ledger line of the pair (it reuses the usage fields when only the report changed).
   - Unless `dryRun`: call `beforeWrite()` (its error goes up) and append the line with `appendFileSync`. When the file does not end with `\n` (a partial last line), write `\n` first.
   Return `{ added, unchanged, live, changing, deferred, missing, errors: [paths] }`.

## Tests

### Unit tests

`apps/dashboard/test/insights.test.mjs`, with a throwaway folder (`mkdtempSync`). Every call passes `file` and `projectsDir` inside that folder, and `isLive: () => false` unless the case says otherwise, so no test reads the real `~/.claude` or runs `pgrep` on real runs. Fixture logs are made-up stream-json lines (one `system`/`init` line, assistant lines with `usage`, and `result` lines with `model_usage_since_last_result.<model>.costUSD`, as in `.claude/scripts/run-usage.selftest.mjs`):

- `runRecord` on a log with two result lines (`costUSD` 2.5 and 1.25) and a report with Launched `2026-11-20 10:00:00`, Mode `pr`, Outcome `needs-you` and a `PR: https://example.test/o/r/pull/7` line: `cost` is 3.75, `costSource` is `model_usage`, `mode` is `pr`, `pr.number` is 7, `launched` is an ISO string, the token sums equal the fixture sums, and the phase costs add up to 3.75 (compared after rounding to cents).
- `runRecord` on a log whose result lines have only `total_cost_usd` (no model usage): `cost` is set, `costSource` is `total_cost_usd`, `tokens` is null, and it does not throw. A mixed log (one line of each kind) sums the tokens of the line with usage only.
- `runRecord` with no report text: the report fields are null and `cost` is still set.
- `runRecord` on a log with no result line: `results` is 0, `cost` is null.

### Harness constraints

- The end-to-end case cannot use a real `pgrep` match for a live run (no `skill-auto-pipeline` process runs in the test): the live rule is checked through `syncLedger({ isLive })` in the unit tests.
- The 20-runs and 40-MB limits of the server are checked through `syncLedger({ limit, maxBytes })` in the unit tests, not by making 21 large runs in the watcher test (slow).

- The tests do not run two real processes that write the ledger at the same moment; the lock is checked through a held lock and a stale lock in the unit tests.
