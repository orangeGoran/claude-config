# Plan: Review loop caps — plan validation back to 4 rounds with an early stop, Codex in verify by default

- **Base**: main
- **Parent**: `.plans/20261124-225819-pipeline-diet-parent.md`

## Goal

Apply the owner's decisions on the round-caps report (25 Nov 2026) to the bootstrap templates, so every bootstrapped project gets them on its next upgrade:

1. `/skill-auto-validate-plan` runs max 4 rounds again, but stops early. A round with no accepted fix (no accepted blocking finding, no regression found, no owner answer that changed the plan) ends the loop. A finding that an earlier round rejected and that comes back unchanged is not acted on again. The last edits of the loop get one cheap self-check instead of a fifth round.
2. `pipeline.codexInVerify` is on by default when the `codex` module is on, so `/skill-4-verify` runs Claude and then Codex in each round.

This plan changes two decisions of the Pipeline diet parent plan: decision 1A of plan 1 (validation max 2 rounds) and the default "Codex out of verify". It is plan 3 of that parent.

Example after the change (made-up project `acme-api`, Codex on):

1. Round 1: Claude and Codex find 2 blocking issues. Both are VALID and fixed. Round 2 runs.
2. Round 2: Codex finds 1 blocking issue (a mistake in a round 1 edit). It is fixed. Claude finds 1 non-blocking wording point. It is applied. Round 3 runs.
3. Round 3: Claude finds no blocking issue. Codex raises the same point that round 1 rejected as INVALID: the decision log marks it `RAISED BEFORE (round 1, F3)` with no edit. One non-blocking edit is applied.
4. No blocking finding was accepted in round 3, so the loop stops. The final edits check reads the round 3 diff, finds no `REGRESSION`, and the status is `READY`. Round 4 does not run.
5. Later, the plan runs. `/skill-4-verify` round 1 is Claude `/code-review`, then Codex `validate-implementation`.

## Context

- Parent plan sections: "Plans, in order" → 1 (Owner decisions: "Plan validation 1A (2026-11-24): `/skill-auto-validate-plan` runs max 2 rounds, not 4 (step 19)"; requirement "Codex leaves verify by default").
- Source data (owner's round-caps report, 25 Nov 2026, not in the repo): share of all blocking plan issues found per round 43 / 27 / 19 / 9 %; requests per plan validation round 51 / 40 / 30 / 22; in 48 % of plans round 3 found a mistake made by round 2's edits; 8 of the bugs that got past verify were found by Codex, not by more Claude rounds.
- Decisions taken for this plan (owner, 2026-11-25):
  - 1A — Plan validation: max 4 rounds, with (a) early stop: a round that accepts no blocking finding and leaves no open `REGRESSION` ends the loop as READY, even when it applied non-blocking edits; (b) a finding that an earlier round rejected and that comes back unchanged is logged `RAISED BEFORE` and not acted on again; (c) when round 4 fixes a blocking item, one check of round 4's edits runs instead of a fifth round. This reverses 1A of the pipeline diet.
  - 2A — `pipeline.codexInVerify` defaults to true when `modules.codex` is on.
- Plan-author choices (not owner decisions; the validators may challenge them):
  - The "final edits check" of (a) and (c) is the three checks of step a (citations, cross-references, propagation), run by the skill on the diff of the last round. It starts no validator, so it costs no full round. It reuses an existing pattern instead of a new Codex prompt (the skill says "Do not write a new prompt").
  - When the final check after round 4 finds no `REGRESSION`, the status is `READY (round 4 edits self-checked)`, so the owner sees that no validator read the round 4 fix. The dashboard does not parse the status (`grep -rn -E "READY|OPEN ITEMS" apps/dashboard/server.mjs apps/dashboard/page/app.js .claude/scripts/plan-lanes.mjs` finds only the plan `status` field `'ready'` in `app.js`, which is a plan header value, not this status).
  - "Blocking" means a finding from the "### Blocking issues" section of a validator report (both report formats have it: `templates/core/dot-claude/agents/plan-validator.md`, `templates/modules/codex/dot-codex/skills/validate-plan/SKILL.md`).
  - An explicit `"codexInVerify": false` keeps Codex out of verify. Only unset changes meaning. No registered project has the field today except this repo (`grep -rl --include=bootstrap.json -s codexInVerify ~/Workspace` lists only this repo and its worktrees, all `true`).
- Open decisions this plan does not take: the open decisions of parent plan 2 (tickets for defects of another repo). Re-measuring verify after about 20 runs of the current design (report caveat) is not part of this plan.
