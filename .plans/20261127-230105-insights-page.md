# Plan: Insights page — /insights, the page switch and the first panels

- **Base**: main
- **Parent**: .plans/20261126-113131-plans-insights-parent.md
- **Waits for**: claude-config plan 20261126-113132-insights-ledger merged

## Goal

Add the Insights page to the plans dashboard: the spend per week and per project, the cost per phase, the run and PR counts, and the plan counts of every project, on one page. The numbers come from the run log that plan 1 writes (`~/.claude/pipeline-dashboard/insights.jsonl`). The page has its own URL (`/insights`), the current page gets `/dashboard`, `/` opens the page that the browser used last, and a click on the page title opens a small menu with the two pages. This is plan 2 of the parent plan ("Plans, in order" → 2).

Example, end to end:

1. The owner opens https://shipyard.test for the first time in a browser. `/` has no query and `localStorage` has no `dash-page`, so the page shows Insights and the address bar changes to `/insights`.
2. The page sends `GET /api/insights`. The server reads the run log (two made-up runs: `demo-api/20261120-100000-add-export` cost 3.75, PR #7, outcome `needs-you`; `demo-web/20261124-090000-fix-header` cost 1.25, outcome `failed`) and the plan files of the two projects, and answers `{ build: 1, runs: [...2 runs], projects: [{ name: 'demo-api', plans: { open: 5, parent: 1, done: 12 } }, { name: 'demo-web', plans: { open: 2, parent: 0, done: 3 } }] }`.
3. The page shows (period 30 days, both chips on): Spend $5.00, Runs 2, Median cost per run $2.50, Draft PRs opened 1, Failed runs 1 (50% of the runs); one stacked bar per week; Cost by phase; the Projects table; the Plans pipeline: Open plans 6, Parent plans 1, Runs started 2, Draft PRs 1, Plans done 15.
4. The owner clicks the `demo-web` chip. The page hides its runs (no new request): Spend $3.75, Runs 1. The choice stays in `localStorage` `dash-insights`.
5. The owner clicks **Plans ▾** and picks **Dashboard**. The page shows the plan list, the address bar is `/dashboard`, and `dash-page` is `dashboard`. The next visit to `/` opens the Dashboard.
6. A notification link `https://shipyard.test/?sel=demo-api/20261120-100000-add-export` still opens that plan on the Dashboard (a query on `/` always means the Dashboard).

## Decisions taken for the owner

- **The title text stays "Plans", with "▾" after it.** The owner wrote "Shipyard ▾"; the page title today is "Plans" (`page.html` `#home`), the Mac app, the docs and a test use that text, and a rename is outside this plan.
- **Plan 1's code names stay; only UI and docs text says "run log".** Plan 1 names `LEDGER`, `readLedger()`, `syncLedger()`, `insights.jsonl` and `insights.jsonl.lock`; renaming them would change a merged plan. This plan renames the docs section "Insights ledger" to "Insights run log", rewords its text and the `AGENTS.md` Commands row, and the page never shows the word "ledger".
- **The server sends the valid runs and the plan counts; the page does the sums.** A period or chip click then needs no request, and the sums are pure page functions that a test runs (the preview works the same way).
- **The date of a run is `launched`, else `ended`.** `launched` is null when the report has no valid Launched line; `ended` is always set by plan 1.
- **A run with `cost: null` counts as a run with $0 spend and is left out of the medians.** It is a finished run without cost data (`results: 0`); a median of $0 would be wrong.
- **A run whose run-log outcome is `running` shows as "ended without a result"** in the sub line of the Failed runs tile (plan 1, Contracts: "plan 2 shows such a run as 'ended without a result'"). The full outcome split is plan 3's Run outcomes panel.
- **The cache: 10 s, keyed by the run log's size and change time, and cleared by every request that is not a GET.** The run log only grows (append), so its size changes on each new line; the plan counts can change by a file edit, which the 10 s covers; a POST (archive, registry) can change the counts at once. No new environment variable.
- **`/` with any query opens the Dashboard and becomes `/dashboard?<query>`.** Notification links (`/?sel=`), scout links (`/?scout=`), `?view=board`, `?settings`, `?tour` and `?guide` keep working.
- **Opening a plan, the Board or the tour from Insights switches to the Dashboard.** These need the plan list and the detail pane, which Insights hides. The drawers (Scout, Settings, Add project, QA reports, Note) open over either page.
- **The period and the hidden chips are kept per browser in `localStorage` `dash-insights`**, as `dash-board-f` keeps the board filters. Default: 30 days (the preview's default), all projects on. The last chip that is on cannot be turned off (the preview rule).
- **The chips list every registered project, then every project that is only in the run log** (a removed project keeps its history); the plan counts come only from registered projects.
- **The Plans pipeline panel ignores the period**, as the preview does ("plan files now, all time"): plan files have no run date.
- **A parent plan is found with the rule of `.claude/scripts/plan-lanes.mjs` (`looksRoadmap`)**, copied, so the dashboard and the lane checker agree.
- **The project colors on the charts come from `projLook()`** (the registry `color`, else the automatic hue), the same as the sidebar.
- **The charts are inline SVG made by the page**, as in the preview. No chart library, so no new CDN load.
- **A week starts on Monday, local time** (the preview's `weekStart()`).
- **The page loads `/api/insights` when Insights opens, then every 60 s while Insights shows.** Insights changes only when a run ends.
- **Insights keeps the Dashboard's open plan aside, not open.** A switch to Insights keeps the Dashboard query (`dashSearch`) and clears `selected`, so a state refresh cannot pull the page back; the Dashboard item gives the plan or the Board back.
- **On `/insights` the path wins over a query** (`/insights?sel=…` shows Insights; the Dashboard item then opens that plan).
- **Two browser tabs on different pages share one `dash-page`; the last switch wins** (the pattern of `dash-tabs`).
- **A partial last line of the run log during a GET is skipped** by plan 1's `readLedger()`; the next build after the write has it (the size changed).
- **Two registry entries with the same `plansDir` each show the plan counts** (counted per entry, no merge). The registry is the owner's; a project chip per entry matches the sidebar.
- **No Mac app menu item in this plan.** In Shipyard the title menu works inside the page; `apps/plans-mac/` is not touched.

## Contracts

- New response `GET /api/insights` (JSON, 200):
  - `build`: a number that goes up by 1 on each new build (the cache test reads it).
  - `runs`: one object per valid run-log line with `v === 1`, newest first by run date: `{ project, slug, launched, ended, mode, outcome, pr, results, cost, phases, minutes }`, copied from the line (from plan 1, not on main yet). `src`, `status`, `tokens` and `costSource` are left out.
  - `projects`: one object per registry entry, in registry order: `{ name, plans: { open, parent, done } }`. `open` is the number of `*.md` files in `plansDir` (the same count as `planFiles()` in `server.mjs`), `parent` the number of those that `isParentPlan()` matches, `done` the number of `*.md` files in `doneDir` (the same count as `doneFiles()`); `planCounts()` in `insights.mjs` counts them itself.
- Consumed contract: the run-log line format `v: 1` of plan 1 (not on main yet), through `readLedger()`.
- Consumers of the new response: only `apps/dashboard/page/app.js`. Plan 3 adds panels on the same response.
- New `localStorage` keys: `dash-page` (`'insights'` or `'dashboard'`), `dash-insights` (`{ days: 7 | 30 | 0, off: [project names] }`).
