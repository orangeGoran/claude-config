# Plan: Make GET /api/state of the plans dashboard fast (server-side caching)

- **Base**: main

## Goal

`GET /api/state` answers in under 1 s with 10 clients polling, and other endpoints stay fast while a state build runs. Today one request takes 7–25 s with about 10 clients, and `/api/usage` takes 0.1–11 s during a state build, because the build is synchronous work that blocks the event loop. This plan has two parts. Fix A reads each project's `.validations/` folder once (not once for each plan) and caches the per-file "has text" check. Fix B makes all requests share one state build and keeps the result for 1 s by default. The JSON body stays the same. This plan does not belong to a parent plan. The roadmap line about the page (`docs/roadmap.md` → **Architecture**, **Page**) gets one sentence about the shared build.

## Contracts

- `GET /api/state` body: unchanged. The new route sends `JSON.stringify(await fullState())` as before, with the same `Content-Type: application/json`. The only difference is that requests in the same window get the same bytes. The window is less than `STATE_CACHE_MS` (1 s by default) after the start of a build, while the build runs and after it ended.
- New response header `X-State-Build: <n>`. `n` is a counter that goes up by 1 for each new state build. Only the tests and `state-load.mjs` read it. The page (`refreshOnce()` in `app.js`) reads only the body (`res.text()`).
- New environment variable `DASH_STATE_CACHE_MS`. The default is `1000`. An empty value, or a value that is not a finite number of 0 or more, also gives `1000`. `0` turns the sharing off: each request makes its own build, as today.
- Consumers of `/api/state` (searched with `grep -rn "api/state" apps scripts skills test`):
  - `apps/dashboard/page/app.js` → `refreshOnce()`. It reads only the body.
  - `apps/dashboard/test/dashboard.test.mjs` (`start()`, `state()`, many tests). They read files that they just wrote, so `start()` gets `DASH_STATE_CACHE_MS: '0'`.
  - `apps/dashboard/test/watcher.test.mjs` (`startServer()` probes `/api/state`, and `plan()` reads it right after the tests change files). So `envFor()` gets `DASH_STATE_CACHE_MS: '0'`.
  - `apps/dashboard/restart.mjs` → `up()`, as a health check only (`res.ok`). It needs no change.
  - `scripts/docs-media.mjs` → `startDashboard()`, as a start probe only. It writes its demo world before the dashboard starts, so it needs no change.
  - The Plans Mac app, which loads the same page.
  - `skills/bootstrap-project/references/contracts.md` documents two body fields of `/api/state`. The body does not change, so it needs no change.
  - None of them reads a header.

## Reference implementation

- Closest existing pattern: the two caches that `server.mjs` already has.
  - `sessionIdsInLog()` with `sessionIdCache`: a per-file cache keyed on `st.mtimeMs + ':' + st.size`.
  - `prLists` with `PR_TTL`: a per-project result with a time-to-live, which the poll reads without waiting.
  - `claudeProcessCwds()` with `claudeCwds = { at, set }`: a short time-to-live (4000 ms) result.
- Files read end to end for this plan: `apps/dashboard/server.mjs` → `validationRounds()`, `hasText()`, `VALIDATOR_REPORT`, `sessionIdsInLog()`, `sessionsIn()`, `listPlans()`, `fullState()`, `enqueueMissingSummaries()`, `planSessions()`, `json()`, the `http.createServer` handler down to the start of the `if (req.method === 'POST')` block, `resolveProject()`, the `--help` text; `apps/dashboard/page/app.js` → `refresh()`, `refreshOnce()`, `claimAlertLead()`, `ringsHere()`, `alertUser()`, the 1 s `setInterval` poll at the end of the file; `apps/dashboard/test/dashboard.test.mjs` → `start()`, `stop()`, `get()`, `post()`, `state()`, `before()`, the tests `stores status and tags`, `the validated count is the number of rounds, with old and new report names` and `docs-media copies a dashboard that starts and serves the page, without the test folders` (the pattern for a second server in its own temp HOME).
- Mirror:
  - `sessionIdCache` (key `mtimeMs:size`) → `textCache` for `hasText()`.
  - `sessionIdsInLog()` (stat, compare the key, else read and store) → `validationIndex(proj)` (stat the folder, compare `mtimeMs`, else `readdirSync` and group the names).
  - `claudeCwds = { at, set }` with a time check → `stateBuild = { gen, n, at, promise }` with `STATE_CACHE_MS`.
  - `DASH_WATCH_MS` → `WATCH_MS` (env parse) → `DASH_STATE_CACHE_MS` → `STATE_CACHE_MS`. Deviation: step 4 also treats an empty value and a value that is not a number as the default, because `+''` is `0` and `+'abc'` is `NaN`.
  - The docs-media test (second server, own temp HOME, `freePort()`, `stop(child)` in `finally`) → the new cache test.
- Deviations:
  - The result cache holds the JSON string, not the object. Then a cached request does not run `JSON.stringify` on 760 KB again.
  - `stateBuild` also holds a promise that is not finished yet. That is how requests that come during a build share the build. `claudeCwds` has no such case because its work is synchronous.
  - The cache window starts when the build starts (`at`), because the build reads the files from that time on. A request shares the last build only while that build is less than `STATE_CACHE_MS` old, whether it still runs or has ended. A request `STATE_CACHE_MS` or more after the start of the last build gets a new build. So a file change shows on the first request that comes 1 s or more after the change, which is within one poll of the 1 s fast mode. The server starts at most one new build in each `STATE_CACHE_MS` window, whatever the number of clients. A build that takes longer than the window can overlap with the next build, which is the same as today for each client. After a clear (`invalidateState()`), a new build can also overlap with the old one. The old build never becomes the shared build again (`stateBuild === b`), and it answers only the requests that came before the clear.
  - `enqueueMissingSummaries()` runs once for each build, not once for each request. It only adds plans to the summary queue, and while a client polls, a build comes at least once for each poll. So the queue fills as early as it does today, within one poll.

## Breaking changes

- `validationRounds(proj, slug)`: the signature and the return value (a number of rounds) stay the same. Callers: `listPlans()` (active rows and archived rows). The watcher (`listPlans()` call in its tick) gets the same values.
- `/api/state`: the body is the same. Requests that come less than `STATE_CACHE_MS` after the start of a build (while it runs or after it ended) get the bytes of that build. A file change shows on the first request that comes `STATE_CACHE_MS` (1 s) or more after the start of the build in use. That is within one poll of the 1 s fast mode of the page, and within one 5 s poll. A non-GET request shows at once on the next GET.
- State that changes in memory with no request (a launcher that exits, the chat flags `chatting` and `chatWaits`, the summary queue) clears no cache. It shows on the first request 1 s or more after the start of the build in use, as a file change does. A file that another file replaces with the same mtime and size counts as unchanged. That is the same limit as `sessionIdCache` has today.
- Test servers that read `/api/state` right after a file change: `dashboard.test.mjs` → `start()` and `watcher.test.mjs` → `envFor()` get `DASH_STATE_CACHE_MS: '0'` (step 7).
- None other.

### End-to-end tests

- The project has no end-to-end harness ("Test (end to end): not available yet" in `AGENTS.md` → **Commands**). The unit tests above already use a real spawned server over HTTP for the changed endpoint. The endpoint has no auth, roles or tenants (local only), so no 401/403/404 cases apply. A slug that is not valid does not reach `/api/state`.

### Harness constraints

- The tests cannot prove the speed (under 1 s with 10 clients, `/api/usage` under 100 ms) or that the folder is listed once for each build. A timing assertion on a small temp fixture would be slow and flaky. These checks go to the manual measurement in **How to verify**, block 2 (`state-load.mjs load` exits 1 when the limits fail), on the real data.
- The tests cannot easily make `fullState()` throw, so "a failed build is not cached, and the next request builds again" is not tested over HTTP. `/skill-4-verify` checks it in code review, against step 4 (the `catch` that sets `stateBuild = null` and throws again, and the 500 from the handler's `catch`).
- The tests do not prove the `finally` case of step 6 for a client that hangs up during an awaited POST. A test would need a POST that waits a controlled time inside the handler. Code review checks it.
- The 500 answer of a failed build is the existing `catch (e)` of the handler (`{ error: String(e) }`). The server answers loopback clients only, and this plan does not change that answer.
- "The JSON for the same files is unchanged" on the real data goes to `state-load.mjs compare` (block 2). In the tests, the existing assertions on row fields prove it for the fixture.

## How to verify

Block 1: tests and checks (the pipeline runs these):

```bash
node --test apps/dashboard/test/dashboard.test.mjs
node --test apps/dashboard/test/watcher.test.mjs
npm test
node .claude/scripts/changelog-validate.mjs --base origin/main
grep -n "DASH_STATE_CACHE_MS" docs/plans-dashboard.md apps/dashboard/server.mjs
grep -n "state-load.mjs" AGENTS.md
```

Block 2: measurement on the real data. Run this from the worktree. Use the real HOME and the watcher off. Each server runs in the background, and you stop each server by its PID, never by name. Never stop or restart the live dashboard on port 4899.

```bash
lsof -ti tcp:4911 -sTCP:LISTEN
lsof -ti tcp:4912 -sTCP:LISTEN
lsof -ti tcp:4921 -sTCP:LISTEN
lsof -ti tcp:4922 -sTCP:LISTEN
git worktree list
DASH_PORT=4911 QA_REPORTS_PORT=4921 DASH_NO_OPEN=1 DASH_WATCH_MS=0 DASH_NO_SUMMARY=1 node <this worktree from git worktree list>/apps/dashboard/server.mjs
DASH_PORT=4912 QA_REPORTS_PORT=4922 DASH_NO_OPEN=1 DASH_WATCH_MS=0 DASH_NO_SUMMARY=1 node <main checkout from git worktree list>/apps/dashboard/server.mjs
node apps/dashboard/state-load.mjs compare 4912 4911
node apps/dashboard/state-load.mjs load 4911 10 60
lsof -ti tcp:4911 -sTCP:LISTEN
ps -p <pid from the line before> -o command=
kill <pid, only when ps shows node … apps/dashboard/server.mjs of this worktree>
lsof -ti tcp:4912 -sTCP:LISTEN
ps -p <pid from the line before> -o command=
kill <pid, only when ps shows node … apps/dashboard/server.mjs of the main checkout>
```

- The four `lsof` lines before the starts must print nothing (exit 1). When a port is taken, take another free port and use it in all later lines. Never stop a process that was there before.
- The sixth and seventh commands start, with absolute script paths, the new server (4911, QA reports on 4921) and the old server of the main checkout (4912, QA reports on 4922), each with `run_in_background`. Each one must answer `GET /api/usage` before the next command runs. A start that fails (its background task ends) means that the port is not ours, so no `kill` runs for it.
- Before each `kill`, `ps` must show the command of the test server that this run started. When it shows any other command, do not stop it, and write that under Open items.
- The run report and the PR carry only the non-verbose output of `state-load.mjs` (numbers and field names), never project names or paths.
- `compare` must exit 0. The run report gives the "info" lines (field names and counts, step 9). When the main checkout is not at the merge base of this branch (`git merge-base HEAD origin/main`), the run report says so, because another merged change can then cause an "info" difference.
- `load` must exit 0: the maximum of `/api/state` is under 1000 ms and the maximum of `/api/usage` is under 100 ms, with 10 clients for 60 s.
- When a headless run cannot start the servers, the run report lists block 2 under Open items for the owner.
